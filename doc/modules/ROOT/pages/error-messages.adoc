= Error messages

When `cerastes verify` cannot prove something, it prints one error per problem,
at the line of the C or pass:[C++] source that causes it:

[source,text]
----
<file>:<line>: error: <category>: <message>
<file>:<line>: note: <what the note says>
----

The *category* names what could not be proved. There are thirteen, and each has a
section below. A *note* line follows an error when a second place matters: the
clause of a contract that failed, or the callee's clause that a call does not
meet. Errors are sorted by file, line and category, and the exit status is 1
when there are any. xref:verifying.adoc[Verifying a program] describes the
command and the other exit statuses.

Every example below is a program that fails with exactly the error named in
its section (the example's line is the one the error points at), followed by
the same program fixed so that it verifies.

[NOTE]
====
cerastes proves that an error cannot happen on any path, with the information
it has: contracts, branches and loop invariants. It does not run your program.
An error means that it could not exclude the problem, and not necessarily that
a run reaches it. To find out which, use the counterexample in your head or a
test; then either fix the code or give the verifier the missing fact.
====

Problems that are not verification errors, for example a program the tool does
not accept, are described in xref:verifying.adoc#not-supported[What is not
supported yet].

== precondition

A call may not satisfy a `CERASTES_REQUIRES` clause of the function it calls. It is reported at the call, with a note that names the clause of the callee.

The verifier could not show that the arguments meet the callee's precondition on every path that reaches the call. Here `use_half` passes `m`, which may be odd, to `half`, which requires an even number.

[source,cpp]
----
include::example$error-messages/precondition_error.cpp[tag=source]
----

[source,console]
----
precondition_error.cpp:16: error: precondition: the precondition of `half` may not hold
precondition_error.cpp:7: note: this is the requirement of `half`
----

*How to fix it.* Either establish the precondition before the call (a test and an early return, or a stronger `CERASTES_REQUIRES` on the caller, as below), or weaken what the callee requires if it does not need it.

== postcondition

A `CERASTES_ENSURES` clause may not hold when the function returns. It is reported at the `return` statement that may leave the clause false (or at the closing brace of a `void` function), with a note at the clause.

The value the function returns, together with what is known about the parameters, does not imply the clause. In the example the function returns one more than the contract allows.

[source,cpp]
----
include::example$error-messages/postcondition_error.cpp[tag=source]
----

[source,console]
----
postcondition_error.cpp:10: error: postcondition: the postcondition of `double_it` may not hold
postcondition_error.cpp:8: note: this is the postcondition
----

*How to fix it.* Change the code so that it returns the right value, or change the contract if it states the wrong thing. If the clause holds only for some arguments, add the condition to `CERASTES_REQUIRES`. Remember that a parameter in a postcondition is its value on entry.

== check

A `CERASTES_CHECK` may not hold. It is reported at the check.

What the verifier knows at that point (the precondition, the assignments and the branches taken) does not imply the condition. A check is a claim for the verifier to prove, and never an assumption.

[source,cpp]
----
include::example$error-messages/check_error.cpp[tag=source]
----

[source,console]
----

----

An `assert(e)` from `<assert.h>` that may fail is reported in the same way, at the `assert`; the message names `assert` instead of `check`.

*How to fix it.* Establish the condition (a stronger precondition or loop invariant, as below), or correct the check.

== invariant-entry

A loop invariant may not hold when the loop is first reached. It is reported at the invariant clause.

The invariant must be true before the first evaluation of the loop condition. In the example `i` starts at 1, so when `n` is 0 the clause `i <= n` is false on entry.

----

----

*How to fix it.* Initialize the variables so that the invariant holds, or weaken the invariant. The error is about the first iteration; an invariant that is wrong later is `invariant-preserved`.

== invariant-preserved

A loop invariant may not hold again after an iteration of the body that started with it true. It is reported at the invariant clause.

The invariant and the loop condition hold at the start of the body, but the body, followed by the loop's increment, may leave the invariant false. Here `i += 2` can step past `n`.

[source,cpp]
----
include::example$error-messages/invariant_preserved_error.cpp[tag=source]
----

[source,console]
----
invariant_preserved_error.cpp:11: error: invariant-preserved: this loop invariant may not be preserved by an iteration
----

*How to fix it.* Change the body so that it keeps the invariant, or strengthen or weaken the invariant until it is both preserved and strong enough to prove what follows the loop. A loop's condition is checked each time it is evaluated, so an arithmetic error in the condition is reported separately.

== overflow

An arithmetic operation may produce a value that does not fit its type, signed or unsigned, or a signed division may be the smallest value divided by -1. It is reported at the operator.

Signed overflow is undefined behaviour in C and pass:[C++], so cerastes treats it as an error rather than assuming it wraps. Unsigned arithmetic is defined to wrap, but cerastes does not wrap it either: `u - v` with `u < v`, a sum or product past the largest value, `-u` for `u != 0`, and `pass:[++]` or `--` past either end of an `unsigned int` (or wider) give this error too, with a message such as "unsigned `unsigned int` addition may overflow (cerastes does not wrap)". See xref:integer-semantics.adoc#unsigned[Integer semantics] for the exact rules. The error also appears for arithmetic inside a contract.

[source,cpp]
----
include::example$error-messages/overflow_error.cpp[tag=source]
----

[source,console]
----
overflow_error.cpp:8: error: overflow: signed `int` addition may overflow
----

*How to fix it.* Bound the operands in a `CERASTES_REQUIRES`, as below, test before computing, or compute in a wider type. If a result modulo 2^N^ is what you mean, write the reduction out (xref:integer-semantics.adoc#modular[Modular arithmetic, written out]).

[source,cpp]
----

== shift

A shift may have a count that is negative or at least the width of the promoted left operand, or a left shift of a signed value may have a negative left operand or a result that does not fit. It is reported at the operator.

In the example the count `n` may be 32 or more, which is undefined for a 32-bit `unsigned`.

[source,cpp]
----
include::example$error-messages/shift_error.cpp[tag=source]
----

[source,console]
----
shift_error.cpp:8: error: shift: the shift count may be negative or at least the width (32 bits) of `unsigned int`
----

*How to fix it.* Bound the count, as below, or mask or reduce it before shifting (`+u << (n & 31)+`). Mind that operands narrower than `int` are promoted first, so the width that matters is the promoted type's. A left shift that may drop bits is fixed the same way: mask the value first, so the result fits (`+(u & 0xFFFFFF) << 8+` for a 32-bit `unsigned u`).

[source,cpp]
----

== conversion

A conversion to an integer type may be given a value that does not fit, signed or unsigned, or a conversion to an enumeration a value that is not one of the enumeration's values. It is reported at the conversion: the cast, the initializer, the assignment, the argument, the `return`, or the operand that C converts for an operator (`-1 < 0u` converts `-1` to `unsigned`).

cerastes does not accept a wrapping conversion, written or implicit: to a signed type the standards disagree on what it means, and to an unsigned type a wrap is almost always a mistake. A conversion to an unsigned type that does not fit is reported as "the value may not fit in `unsigned char` (a conversion must be exact)". This includes `pass:[uc++]` and `uc += 1` on an `unsigned char` holding 255, which compute in `int` and convert back.

[source,cpp]
----
include::example$error-messages/conversion_error.cpp[tag=source]
----

[source,console]
----
conversion_error.cpp:9: error: conversion: the value may not fit in `signed char` (a conversion to a signed type must be exact)
----

*How to fix it.* Bound the value so that it fits, as below, or reduce it yourself before converting (`(unsigned char)(x % 256)` or `+(unsigned char)(x & 255)+` for `x >= 0`). A mask written as a negative `int` converts too: `+u & ~7+` with an `unsigned u` converts `+~7+`, which is -8, to `unsigned int`; write `+u & ~7u+` (xref:integer-semantics.adoc#bitwise[Bitwise operators]).

[source,cpp]
----
include::example$error-messages/conversion_fixed.cpp[tag=source]
----

A conversion to an enumeration is checked against the enumeration's values
(xref:integer-semantics.adoc#enumerations[Enumerations]), also when the
enumeration's underlying type is unsigned:

[source,c]
----
include::example$integer-semantics/enumeration_range.c[tag=source]
----

[source,console]
----
enumeration_range.c:11: error: conversion: the value may not be one of the values of `enum color` (0 to 3)
----

*How to fix it.* Bound the value with a `requires` or a test before the cast.

== missing-return

A function that returns a value may reach its closing brace without a `return`. It is reported at the closing brace.

Flowing off the end of a non-`void` function is undefined behaviour in pass:[C++] and C when the caller uses the result. The only exception is `main`, which returns 0.

== termination

A termination measure (`CERASTES_DECREASES`) may be negative, or may not decrease. For a loop it is reported at the loop's `CERASTES_DECREASES` clause, and for a recursive function at the recursive call, with a note at the callee's measure. A recursive call that another call of the same expression may precede (`f(n - 1) + f(n - 2)`) is checked where C may make it, before the other call, and reported the same way (xref:verifying.adoc#calls[Calls in expressions]).

The measure must get smaller from one iteration to the next (for a function, from the entry to each recursive call), and must not be negative when the loop condition holds. A measure that stays the same, grows, or can go below zero does not show that the loop or recursion ends, so cerastes does not accept it. In the example the body forgot to add 1 to `i`.

[source,cpp]
----
include::example$error-messages/termination_error.cpp[tag=source]
----

[source,console]
----
termination_error.cpp:12: error: termination: the measure of this loop may not decrease, or may not be bounded below by zero
----

*How to fix it.* Change the code so that the measure decreases, as below, or choose a measure that does: for a loop that counts up to `n`, the distance `n - i` to the bound. A measure with several expressions is compared lexicographically (see xref:verifying.adoc[Verifying a program]). The measure's own arithmetic is checked too: an overflow in it is an `overflow` error at the measure.

----

== noreturn

A function declared not to return (with the attribute `noreturn`, or with `_Noreturn` in C) may return. It is reported at the `return` that may be reached, or at the closing brace.

Returning from such a function is undefined behaviour in C and pass:[C++]: its callers are compiled, and verified, as if the call never comes back. Every path through its body must end in a call of another function that does not return, such as `abort` or `exit`.

[source,c]
----
include::example$error-messages/noreturn_error.c[tag=source]
----

[source,console]
----
noreturn_error.c:14: error: noreturn: `fail_if` is declared not to return, but control may reach its end
----

*How to fix it.* Make every path end in a call that does not return, or remove the attribute `noreturn`. A function that ends the program only on some inputs is better written without the condition, with the test at the call:

[source,c]
----
include::example$error-messages/noreturn_fixed.c[tag=source]
----

The contract of `check_positive` is what its callers rely on: the path through `fail()` ends the program, so only the path that returns has to satisfy `r > 0`.

== uninitialized

A local variable may be read before it has a value. It is reported at the read.

A variable declared without an initializer has no value until it is assigned:
reading it first is undefined behaviour in C and in pass:[C++] (erroneous
behaviour in pass:[C++]26), and it is the first thing the pass:[C++]
initialization profile forbids (P4222). Look for a path that reaches the read
without passing an assignment: a branch that does not assign the variable, a
loop that may run zero times, a `switch` without `default`, or a `goto` or `case`
label that jumps past the assignment, or a read that comes before an assignment in
the same expression (`(y = x, x = 1)`). A read is any use of the value, including
the old value in `x += 1` or `pass:[x++]`, a `return`, an argument, and an annotation
such as `CERASTES_CHECK` or a loop invariant (there it is reported where the
invariant is checked).

----

or initialize it where it is declared. cerastes follows the paths of the
program, so the assignments need not be in the same branch as the read, only on
every way to it:
