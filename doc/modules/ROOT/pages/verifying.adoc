= Verifying a program

`cerastes verify` checks a C or pass:[C++] source file against the contracts
written in it. It proves, for every function with a body, that the
postconditions hold, that every call meets the callee's precondition, that
every `CERASTES_CHECK` and loop invariant holds, that no integer
operation overflows, divides by zero or shifts out of range, and that every
loop and every recursive function terminates. When it cannot prove one of
these, it reports the line. This page describes the command,
what it verifies, what it prints and the assumptions a result rests on.

The annotations are described in xref:annotations.adoc[Annotations]. The
meaning of the integer operations is in xref:integer-semantics.adoc[Integer
semantics], and every message the tool can print is in
xref:error-messages.adoc[Error messages].

== Running it

[source,sh]
----
build/cerastes verify midpoint.cpp
----

The file is the one source file of the run. It is this function:

[source,cpp]
----
include::example$verifying/midpoint.cpp[tag=source]
----

[source,console]
----
midpoint.cpp: verified (1 function; one translation unit: assumes that functions defined elsewhere satisfy the contracts declared here)
----

The command takes these options and no others. An option that is not in this
table is refused with exit status 2, even if the front end would accept it:
verification must not depend on a diagnostic that was switched off or a
dialect that was changed behind its back.

[cols="2,5"]
|===
| Option | Meaning

| `-I<dir>`, `-I <dir>`
| Add `<dir>` to the user include path.

| `-D<name>[=<value>]`, `-U<name>`
| Define or undefine a macro. `+__CERASTES__+` is defined by the tool and cannot be
  defined or undefined. The names the annotations depend on
  (`+__has_cpp_attribute+`, `+__has_c_attribute+`, `cerastes`, `requires`,
  `+CERASTES_H+` and every `CERASTES_*` macro) are refused too.

| `--std=pass:[c++20]`, `--std=c23`
| The language mode. The default is `c23` for a `.c` file and `pass:[c++20]` for
  anything else. GNU dialects and C before C23 are not accepted.

| `--keep-vpr`, `--keep-vpr=<path>`
| Keep the generated Viper program and its position map. See
  <<keep-vpr>>.

| `--timeout=<seconds>`
| The wall-clock limit for the proof search. The default is 300. Reaching it is
  a failure of the tool, not a verdict on your program (exit status 3).

| `--help`, `--version`
| Print usage, or the version.
|===

The tools the verifier runs (the Java runtime, Silicon, Z3 and the system
include directories) are fixed when cerastes is built. Environment variables
such as `SILICON_JAR` or `Z3_EXE` do not change a result.

== What is verified

cerastes verifies the *primary file and every user header it includes*: each
function body in them. A header is verified again in every run that includes
it.

A *system file* is not verified. It is a file under one of the system include
directories the tool was built with (the SDK, the pass:[C++] library, the
compiler's own headers), or exactly the `include/cerastes.h` of the cerastes
checkout. The test is made on the file's real path (symbolic links and `..`
are resolved), never on a flag in the source, so a `#pragma` or a `#line` in
your code cannot turn the checks off. A `#line` directive in a verified file is
rejected for the same reason. A function declared in a system file is used only
through a contract; its body is never read.

A directory you give with `-I` is a user directory, even if it holds
library code.

The bodies of functions marked `CERASTES_PREDICATE` and `CERASTES_PURE` are
specification and are not verified. In this version a call of one of them in
executable code is rejected, and in a contract only `cerastes::old` may be
called.

== The output

A verification error is one line on standard output, followed by notes that
say which clause is involved:

[source,console]
----
midpoint_overflow.cpp:10: error: overflow: signed `int` addition may overflow
----

The file is written as you gave it on the command line (or as the include
resolved, for a header), the line is the line of the C or pass:[C++] source,
and the category is one of eleven names that
xref:error-messages.adoc[Error messages] explains. Errors are sorted by file,
then line, then category, and each is printed once. A program with errors
exits with status 1.

[source,cpp]
----
include::example$verifying/midpoint_overflow.cpp[tag=source]
----

A program that cerastes does not accept, because EDG finds a compile error
or because it uses a construct that cerastes does not verify, is reported
on standard error in EDG's format, with the diagnostic's name, and the exit
status is 2. Standard output is then empty:

[source,console]
----
"rejected_double.cpp", line 6: error #cerastes-unsupported_type: type "double" is not supported by "cerastes verify": only integer types, bool and the enumerations of the verified files are (decisions 0012 and 0018)
  double half(double x)
         ^

1 error detected in the compilation of "rejected_double.cpp".
----

Nothing else is printed. In particular a warning from the front end in a
verified file is shown on standard error like any diagnostic, so a program
that is meant to verify cleanly should compile without warnings.

== Exit status

[cols="1,6"]
|===
| Status | Meaning

| 0 | Every function verified.
| 1 | Verification errors, printed on standard output.
| 2 | The program is not accepted: a front-end error, a construct cerastes does not verify, a refused option or a missing file.
| 3 | The tool failed: the prover crashed, timed out or gave no verdict, an error could not be traced to a source line, the front end aborted with an internal error, or cerastes found an inconsistency in its own encoding (reported as "an internal inconsistency"). This is never a statement about your program.
|===

== Loops and termination

A loop needs an invariant to be verified (the verifier does not unroll it) and
a *measure*, `CERASTES_DECREASES(...)`, to show that it ends. The invariant
must hold when the loop is first reached and after every iteration, and what
follows the loop is proved from the invariant and the negation of the
condition. The measure is one or more integer expressions that get smaller
with every iteration and never go below zero: in `n - i`, the loop condition
`i < n` makes it positive, and `i += 1` makes it smaller. The arithmetic in the
loop is checked on every iteration, and so is the condition each time it is
evaluated, and so is the arithmetic of the measure.

[source,cpp]
----
include::example$verifying/loop.cpp[tag=source]
----

Here the invariant `s == 2 * i` and the bound `i <= n` give `s == 2 * n` when
the loop ends, and the measure `n - i` shows that it ends. A loop with no
`CERASTES_INVARIANT` is verified with only the facts the verifier derives
automatically (that each variable the loop assigns stays in the range of its
type), which is rarely enough to prove anything about the result.

A recursive function needs a measure too, written after its parameter list. It
is compared from the entry of the function to every call of a function in the
same recursion cycle, over the arguments of the call:

[source,cpp]
----
include::example$verifying/recursion.cpp[tag=source]
----

A measure with several expressions is compared lexicographically: at the first
one that changes, the new value must be smaller than the old one, which must
not be negative, and the later ones may be anything. A function that is not in
a recursion cycle needs no measure. A loop, or a function in a cycle (direct
recursion, or mutual recursion through other functions of the file), without
one is rejected, because a program whose termination is not shown cannot be
called verified:

[source,cpp]
----
include::example$verifying/missing_measure.cpp[tag=source]
----

The errors a wrong invariant or measure can cause are `invariant-entry`,
`invariant-preserved` and `termination`, described in
xref:error-messages.adoc[Error messages].

[#control-flow]
== Leaving a loop early: break, continue, do and switch

`break` leaves a loop, or a `switch`, at once, without evaluating the loop's
condition, so the invariant is not checked there. What follows the loop is
proved from the way it was left: the invariant and the negated condition, or
the state at one of the `break` statements. `continue` ends the iteration: in a
`for` loop the increment runs, then the condition is evaluated again, so the
invariant and the measure are checked there as at the end of the body.

[source,c]
----
include::example$verifying/control_flow.c[tag=source]
----

In `smallest_divisor` the loop ends either at the `break`, where `n % d == 0`,
or when `d < n` is false, where the invariant gives `d == n`; both give the
postcondition.

A `do` loop runs its body before its first test, so its invariant holds at the
start of every iteration (on entry, and each time the test is true), and the
arithmetic of its condition is checked after the body, where the condition is
evaluated. `CERASTES_INVARIANT` and `CERASTES_DECREASES` are written before
`do`. A `do { ... } while (0)`, whose body runs once, needs no measure; a
condition that names a variable, even a constant equal to zero, makes it an
ordinary loop that needs one.

A `switch` evaluates its controlling expression once, with the usual checks,
and goes to the matching `case` label, to `default`, or past the `switch`.
Execution falls through from one label's statements to the next until a
`break`; `+[[fallthrough]];+` (or `+[[gnu::fallthrough]];+`) marks an intended
fallthrough for compilers that warn about it. Each `case` value is checked as it
is written, like any constant: `case 1 << 40:` is a `shift` error at the label,
even where the compiler only warns. The `case` values are checked at the start
of the function, whether or not the `switch` is reached, and in pass:[C++] they
may name constants (<<constants>>). A `switch` on an enumeration must also pass
the compilers' `-Wswitch` rules (xref:integer-semantics.adoc#enumerations[Enumerations]).
A label may jump past a declaration without an initializer: the variable has no
value there until it is assigned (<<uninitialized>>). cerastes rejects a `case` or `default` label that is not directly
inside the braces of its `switch` (as in Duff's device), a GNU case range
(`case 1 ... 3:`), a statement other than a declaration without an initializer
before the first label, a declaration with an initializer that a later label
jumps over, and a `switch` with an init-statement or a declaration in its
condition.

[#goto]
== Jumping forward with goto

A `goto` is verified when it jumps *outward and forward*: its label is a later
statement of a block that encloses the `goto`, and no declaration of that block
lies between them. That covers the usual uses: an early exit to a common label
at the end of a function, a cleanup label, and leaving nested loops or a
`switch` at once. As with `break`, the loop's condition is not evaluated on the
way out, so its invariant is not checked there; after the label, what follows is
proved from each way of getting there.

[source,c]
----
include::example$verifying/goto_exit.c[tag=source]
----

After `done:`, the postcondition is proved for each way of getting there: from
either `goto`, where `result` is still -1, and from the subtraction, which
cannot overflow because `0 <= y <= x` holds there.

A `goto` may jump past a declaration without an initializer; the variable has
no value at the label until it is assigned (<<uninitialized>>). cerastes rejects
a `goto` that jumps backward (write the loop as `while`, `for` or `do`), one that
jumps into a block, an `if` branch, a loop or the body of a `switch`, one that
jumps past a declaration with an initializer that is still in scope at the
label (the initialization would be skipped), and the GNU computed `goto`.

[#uninitialized]
== Locals without an initializer

A local may be declared without an initializer and given its value later. Until
it is assigned it has no value: reading it is undefined behaviour in C and in
pass:[C++] (erroneous behaviour in pass:[C++]26), and the first rule of the
pass:[C++] initialization profile (P4222) forbids it. cerastes checks every
read. A read that may come before the variable has a value is an
`uninitialized` error at the read
(xref:error-messages.adoc[Error messages]). The check follows the
paths of the program, so a variable assigned on every path that reaches the
read verifies, even when the assignment is in another branch than the read:

[source,c]
----
include::example$verifying/uninitialized.c[tag=source]
----

In `pick`, `x` is read only when `c` is non-zero, and then it was assigned.

A read is any use of the value: in an expression, a condition, a `return`, an
argument, the old value in `x += 1` or `pass:[x++]`, and an annotation such as
`CERASTES_CHECK` or a loop invariant. Each time its declaration is reached, in
the next iteration of a loop for example, the variable has no value again. A
`goto` or a `case` label may jump past a declaration without an initializer, as
C and pass:[C++] allow; the variable then has no value at the label until it
is assigned. A `const` local without an initializer is rejected, since it can
never be given a value. cerastes is stricter than pass:[C++] in two cases:
copying an indeterminate `unsigned char` is allowed there and an error here,
and an expression statement that only names the variable (`x;` or
`(void)x;`) does not read it in pass:[C++], while cerastes counts it as a read,
as C does. An operand of `sizeof` is never a read.

[#side-effects]
== Side effects in expressions

An assignment, a compound assignment and `pass:[++]` or `--` may be used as a
value, and the comma operator may join expressions, in both modes:

[source,c]
----
include::example$verifying/expressions.c[tag=source]
----

The value of `x = e` is the value stored in `x`: `e` converted to the type of
`x`, which is checked like every conversion (xref:integer-semantics.adoc[Integer
semantics]). The value of `x += e` and of `pass:[++x]` is the new value of `x`,
the value of `pass:[x++]` the old one. In `a, b` the left operand is evaluated
completely, then the right one, whose value is the value of the whole
expression. A side effect in the right operand of `&&` or `||`, or in an arm of
`?:`, happens only when that operand is evaluated, and one in a loop condition
happens each time the condition is evaluated: the loop invariant holds before
each evaluation. A variable assigned inside an expression has its value from
that point on (<<uninitialized>>).

The last evaluation of a loop condition counts too. In `count_up` the condition's
`pass:[i++]` runs once more than the body, so after the loop `i` is `n + 1`;
returning `total + i - 1` instead gives `3 * n`, and the postcondition fails at
the `return`:

[source,c]
----
include::example$verifying/expressions_error.c[tag=source]
----

C leaves the order in which most operands are evaluated unspecified, and an
expression that modifies a variable and also reads or modifies it in an operand
that is not sequenced with the modification is undefined behaviour. cerastes
rejects such an expression at the modification, by C's rules in both modes,
even where pass:[C++]17 defines it (`x = pass:[x++]`):

[source,c]
----
include::example$verifying/unsequenced.c[tag=source]
----

The same holds for an object in memory that the expression names twice in the
same way: a variable whose address is taken, or `*p` through one pointer
variable `p` (`*p = pass:[(*p)++]`, `pass:[(*p)++] + *p`), which GCC's
`-Wsequence-point` reports. Two accesses that name objects in different ways but
may meet (`*p = pass:[(*q)++]`) are checked per path instead, and reported as
xref:error-messages.adoc#_unsequenced[`unsequenced`]
(xref:memory.adoc#expressions[Memory and ownership]).

The operators that sequence their operands are `&&`, `||`, `,` and the condition
of `?:`; both arms of `?:` count as modifying what either arm modifies. The
operands of the other operators, and the arguments of a call, are not
sequenced. As with `-Wswitch`, a few shapes that the compilers' `-Wall` warns
about are rejected too: an assignment used as a condition without extra
parentheses (write `if ((x = e) != 0)` or `if ((x = e))`, not `if (x = e)`), a
comma operator one of whose operands has no effect, a discarded value computed
around a side effect (`pass:[x++] + 1;`), a side effect inside `sizeof`, which is
never evaluated, and an assignment of a variable to itself (`x = x`, and also
`x &= x` and `x |= x`, which Clang's `-Wself-assign` reports; written through a
macro, or with an explicit cast, it is accepted, as Clang accepts it). A `|=`
as the whole condition (`if (x |= a)`) counts as an assignment used as a
condition. The bitwise operators have shapes of their own
(xref:integer-semantics.adoc#bitwise[Bitwise operators]), and so do comparisons,
shifts and conditions (<<warning-shapes>>).

A `?:` whose arms are `void`, written as a statement, means the `if` it
abbreviates: `c ? v(x) : w(y);` is verified as `if (c) v(x); else w(y);`, so each
arm's checks hold on its own path. This holds also for an operand of a `,` whose
value is not used and for the step of a `for` loop:

[source,c]
----
include::example$verifying/void_conditional.c[tag=source]
----

Such a `?:` has no value, so using one as a value is rejected: as the left
operand of a `,` whose value is used, and, in pass:[C++], in
`return c ? v() : w();` in a function that returns `void` (write the `if`).

[#warning-shapes]
== Shapes the compilers warn about

Some expressions are valid C and pass:[C++] but rarely mean what they say, and
clang or GCC warns about them by default or with `-Wall`. cerastes rejects them,
in both modes and also in annotations, even when only one compiler warns, in one
language (the body of a `CERASTES_PREDICATE` or `CERASTES_PURE` function is not
verified yet, so these rules do not reach it either):

* `&&` as an operand of `||` without parentheses: `a && b || c` (write
  `(a && b) || c`);
* `{plus}` or `-` as an operand of a shift without parentheses:
  `+a + b << c+`, `+a >> b - c+` (write `+(a + b) << c+`);
* `!x` as the left operand of a comparison whose right operand is not a truth
  value: `!x == y`, `!x < y`, `!x == 0` (write `!(x == y)` or `(!x) == y`);
* a comparison as an operand of another comparison without parentheses:
  `+a < b < c+`, `a == b == c`, `+a < b == 1+`;
* a comparison of a variable with itself (`x == x`, `+x >= x+`), or of two
  equal expressions without calls (`pass:[x + 1 == x + 1]`); a comparison written
  inside a macro (`assert(x == x)`) is accepted, as the compilers accept it,
  except in an annotation, where `CERASTES_REQUIRES(x == x)` is rejected;
* a truth value compared with a constant that gives the same result whether it
  is false or true: `+(a > b) == 2+`, `+(a > b) >= 0+`, `p == 2` for a
  `bool` `p`;
* in a condition (of `if`, `while`, `do`, `for` and `?:`, an operand of `!`,
  `&&` and `||`, a conversion to `bool`, and the condition of an annotation, an
  `assert` or a static assertion): a shift left whose result is signed
  (`+if (a << b)+`), a multiplication (`pass:[if (a * b)]`), a `?:` with a
  constant arm other than 0 and 1, or an enumerator whose value is neither 0 nor
  1 (write `+(a << b) != 0+`);
* arithmetic on values of two different enumerations (`pass:[RED + NA]`) and a
  `?:` whose arms are (`x ? RED : NA`), which pass:[C++]20 deprecates;
* a constant as the right operand of `&&` or `||` (`x && 4`, `x || 2`, also
  `x && 1`), unless the left operand is a `bool` or the operator comes from a
  macro (`assert(x && 4)`);
* in code, a comparison with a literal or an enumerator that the other
  operand's type cannot hold (`uc == 300` for an `unsigned char` `uc`,
  `+x < 3000000000LL+` for an `int` `x`);
* two comparisons of the same variable with constants, joined by `&&`, that can
  never both hold, or by `||`, one of which always holds (`+x > 5 && x < 3+`,
  `x == 1 || x != 1`), in code outside macros (in an annotation such a contract
  is accepted);
* an `else` that belongs to an inner `if` written without braces
  (`if (a) if (b) x = 1; else x = 2;`): write the braces;
* a lone `;` as the body of an `if` without `else` or of a `switch`
  (`if (x > 0);`), even on the next line or after a macro that expands to
  nothing: write `{}`;
* returning the address of a local variable or a parameter (`return &x;`, also
  through parentheses, a cast, either arm of `?:` or the right operand of `,`),
  which clang's `-Wreturn-stack-address` and GCC's `-Wreturn-local-addr` report
  (xref:memory.adoc[Memory and ownership]).

[source,c]
----
include::example$verifying/warning_shapes.c[tag=source]
----

The shapes of <<side-effects>> and of
xref:integer-semantics.adoc#bitwise[Bitwise operators] are rejected the same
way. GCC's `-Wextra`-only warnings, such as `+u >= 0+` for an unsigned `u`,
`else ;` and `do ; while (c);`, are not: such a comparison is simply true. A few
warnings are not checked yet, among them `if ((x == y))`, `switch (a > b)`,
misleading indentation and an empty loop body `while (x--);`.
`pass:[RED == RED]` is accepted too: the front end replaces it by its value
before cerastes sees it.

[#calls]
== Calls in expressions

A call may appear anywhere in the code of a function: as an operand of any
operator, in the second operand of `&&` or `||`, in an arm of `?:` and in the
condition of a loop. Each call is checked against the contract of the function
it calls, where it is made: its `CERASTES_REQUIRES` at the call, and its
`CERASTES_ENSURES` known after it. A call in the second operand of `&&` is made
only when the first operand is true, so its precondition may rely on the first
operand, and a call in a loop condition is made, with its precondition checked,
each time the condition is evaluated:

[source,c]
----
include::example$verifying/calls.c[tag=source]
----

With the guard `a >= 0` instead, `pos` may be called with 0, which its
precondition excludes, and the precondition fails at the call:

[source,c]
----
include::example$verifying/calls_error.c[tag=source]
----

C does not say in which order it calls two functions of one expression that are
not nested in each other and not separated by `,`, `&&`, `||` or the condition
of `?:`: in `f(a) + f(b)` either call may come first, and every order must be
correct. A function that does not return (one that calls `exit`, even on some
inputs only) stops the program before anything C would have evaluated after it,
so a check C may evaluate first must be checked first. cerastes accepts such an
expression when its checks can be put in one order: each check depends on the
calls C must have finished before it evaluates the check (the calls whose
results it uses, and the calls its guard and the earlier operands of a `,`
contain),
and for any two checks, the calls one depends on must be among the calls the
other depends on. It then checks each one as early as C can evaluate it. When two checks each depend on a call the other does not, as in
`100 / f(x) + 100 / g(y)`, the expression is rejected (`unsequenced_calls`);
giving each call its own statement fixes the order:

[source,c]
----
include::example$verifying/unsequenced_calls.c[tag=source]
----

C finishes the first operand of `,` before it uses the value of the second, and
every argument before it makes the call, so a check of that value, and the
`CERASTES_REQUIRES` of the function called, come after those calls. A function
that ends the program unless its argument is valid can therefore guard the use
of that argument within one expression:

[source,c]
----
include::example$verifying/comma_order.c[tag=source]
----

Storing a result is not a check: `(x = f(a)) + (y = g(b))` gives `x` and `y` the
same values in every order, and is accepted:

[source,c]
----
include::example$verifying/call_writes.c[tag=source]
----

An operand that C evaluates only on one path (the second operand of `&&` or
`||`, an arm of `?:`) still counts like a check, even when it only assigns.

The checks of a call count too: each `CERASTES_REQUIRES` clause of the function
called, which depends on every call in the arguments, and the conversion of each
argument to its parameter's type, which depends only on the calls in that
argument. So `g(f(x), h(y))` is accepted when `g` has one `CERASTES_REQUIRES`
clause about each argument, and rejected when `g` has `short` parameters that
`int` results must be converted to, since each conversion depends on one call;
`int` parameters keep it accepted.

When the checks cannot be put in one order this way, cerastes tries once more
with each `CERASTES_REQUIRES` clause depending only on the calls in the arguments
it reads, and the value of a `,` only on the calls of its second operand, and
accepts the expression if that gives one order. Those checks then come earlier
than C may evaluate them, which can report an error on a path C never takes (a
false alarm), never miss one. In `h(f(x), y) + 100 / g(z)`, where the
`CERASTES_REQUIRES` of `h` reads only its second argument, the precondition of
`h` is checked before `f` is called: if `f` could end the program on the inputs
where the precondition fails, the report is a false alarm. Giving `f(x)` its own
statement removes it.

A recursive call that another call of the same expression may precede, as in
`fib(n - 1) + fib(n - 2)`, has its termination measure (`CERASTES_DECREASES`)
checked where C may make it, before the other call, and a failure is reported at
the recursive call (xref:error-messages.adoc#_termination[termination]).

[#no-return]
== Functions that do not return

A function declared `+[[noreturn]]+` (or `_Noreturn` in C, or with the GNU
attribute `noreturn`) must never return: cerastes checks that no `return` and no
closing brace of its body can be reached, and reports one that can as a
`noreturn` error. A call of such a function ends the path of its caller, so what
would follow it is not checked.

`abort`, `exit` and `_Exit` from `<stdlib.h>` are known not to return. They are
the only functions of the C library that cerastes knows so far; `quick_exit`,
`+__builtin_trap+`, `+__builtin_unreachable+` (and C23's `unreachable()`) and
`std::terminate` are rejected.

[source,c]
----
include::example$verifying/no_return.c[tag=source]
----

Without the call of `fail`, `a / b` would be a `division-by-zero` and an
`overflow` error. A function declared not to return cannot have
`CERASTES_ENSURES` (it would never be checked), and `main` cannot be declared not
to return. A function that never returns by looping forever is rejected, since
every loop needs a measure.

[#assert]
== assert

`assert(e)` from `<assert.h>` (or `<cassert>`) is verified as a check of `e`: a
failure is a `check` error at the `assert`. Unlike `CERASTES_CHECK`, it is code:
`e` is evaluated at run time, so its arithmetic is checked like any expression's,
and it may call functions. When `NDEBUG` is defined, `assert` does nothing, and
cerastes checks nothing, as the program will run. A result holds for the
configuration that was verified: with asserts on, the code after `assert(e)` may
rely on `e`, which a build with `NDEBUG` no longer checks, so verify the
configuration you ship.

[source,c]
----
include::example$verifying/assert.c[tag=source]
----

Here the `requires` keeps `sum` small, the `assert` states a bound that the `requires` guarantees, and the contract pins the result exactly: `r == (a + b) / 2`.

[#constants]
== Named constants

A `const` variable at file scope (in pass:[C++] also `constexpr`, and at
namespace scope) whose initializer is a constant can be used anywhere: in code,
in `CERASTES_REQUIRES`, `CERASTES_ENSURES`, `CERASTES_CHECK`, invariants and
measures. In pass:[C++] it can also be named in the initializer of another
constant and be a `case` value, and so can a local `const` or `constexpr`
variable initialized with a constant (`case LIMIT:`, `case LIMIT + 1:`,
`case k:`).

[source,c]
----
include::example$verifying/named_constants.c[tag=source]
----

A constant's initializer is checked as you wrote it, like any constant
(xref:integer-semantics.adoc#constants[Integer semantics]), at the start of every
function in the file, whether or not the function uses it, so the error is
reported at the constant even when nothing reads it:

[source,c]
----
include::example$verifying/named_constants_error.c[tag=source]
----

[source,console]
----
named_constants_error.c:7: error: shift: the shift count may be negative or at least the width (32 bits) of `int`
----

Until it is fixed, such an error hides the other errors of the file. The `case` values of a function
are checked the same way, at its start, so a bad `case` value is reported even
where the `switch` is never reached.

Rejected: a global variable that is not `const`; a `const` declared `extern`
and not defined in the file; in C, `const int z;` without an initializer (another
file may define `z`, and the linker would use its value: write `= 0`, or make it
`static`); a weak constant (`+__attribute__((weak))+`, `+#pragma weak+`), whose
value another file may replace; a constant initialized by running code (in
pass:[C++], an initializer that is not a constant expression, such as
`const int n = f();`); `volatile` and `thread_local` constants; a global
declared in a system header. In C, a constant cannot be named where the language
requires a constant expression (a `case` value, `_Static_assert`, the
initializer of another file-scope constant): a `const` object is not a constant
expression in C, although some compilers accept it, so the front end refuses it.
C23's `constexpr` objects are not accepted by the front end yet.

[#static-assertions]
== Static assertions

A `static_assert` (`_Static_assert` in C) is checked as you wrote it, with
cerastes's integer rules, at block, file and namespace scope. The compiler has
already found its condition true, but in its own arithmetic, where an unsigned
product may wrap and, in C, a shift may lose bits. cerastes reports an
`overflow`, `shift` or `conversion` in the condition at its line, whether or not
the function that holds it is ever called, and then checks that the condition
holds:

[source,c]
----
include::example$verifying/static_assert.c[tag=source]
----

[source,c]
----
include::example$verifying/static_assert_overflow.c[tag=source]
----

Like a named constant's initializer, a static assertion is checked at the entry
of every function it applies to (a file-scope one in all of them), so a failing
one is reported once and hides the other errors of those functions until it is
fixed. A static assertion in a function body is checked wherever it stands (in
a loop, a `switch` or a nested block), except in the body of a
`CERASTES_PREDICATE` or `CERASTES_PURE` function, which is not verified yet.

A condition that calls a function (`std::numeric_limits<int>::max()`), uses a
type trait (`std::is_integral_v<int>`, `+__is_integral(int)+`) or a concept
(`std::integral<int>`), or names a variable or enumerator of a system header, is
not checked by cerastes in this version: the compiler checks it, and nothing at
run time depends on it. Type traits are planned before generic templates. The
types it names are still checked, as everywhere (<<not-supported>>):
`std::is_same_v<char[4], char[4]>` is rejected for its array type.

[#keep-vpr]
== Keeping the Viper program

cerastes translates the program to Viper, the verification language of the
Silicon prover, and Silicon asks Z3. `--keep-vpr` writes the Viper text and
the position map that links each checked line of it to your source:

[source,sh]
----
build/cerastes verify midpoint.cpp --keep-vpr
----

This writes `midpoint.vpr` and `midpoint.vpr.map` into the current directory.
`--keep-vpr=<path>` writes `<path>` and `<path>.map`. The files are written for
every run that reaches the prover (exit status 0, 1 or 3), whatever the
verdict. They are for people who want to see what was checked; the reports
already point at your source, never at the Viper file.

== The single-unit assumption

A result is for one translation unit. A contract you declare for a function
that is defined elsewhere, in another source file or in a library, is
*trusted*: the callers in this unit are verified against it, and nothing here
checks that the definition satisfies it. The success line says so. The
definition is checked when the file that contains it is verified; a library
function that is never verified is trusted for good.

[source,cpp]
----
include::example$verifying/declared_elsewhere.cpp[tag=source]
----

Here `two_ids` is verified assuming `next_id` meets its contract. A function
that has neither a contract nor a body in a verified file cannot be called from
verified code: the call is rejected, because there is nothing to verify it
against.

The same holds for constants: a constant's value is the one in this file. In
pass:[C++] a namespace-scope `const` has internal linkage, so the file that
defines a function whose contract you trust may give a constant of the same
name another value; keep such constants in one header that both files include.

And for enumerations: a value of an enumeration is assumed to be one of its
values (xref:integer-semantics.adoc#enumerations[Enumerations]) when it comes
from outside the verified code, as a parameter or as the result of a function
whose contract you trust. Every conversion into an enumeration in verified code
is checked, but C lets code in another file store any value of the integer type
the compiler picks for the enumeration, and such a value is outside what the
result covers.

== What a result means

A verified function terminates on every input that satisfies its `requires`,
has no undefined behaviour on the way, and returns a value that satisfies its
`ensures`, or ends the program by calling a function that does not return (such
as `abort` or `exit`): the result is *total correctness*. A call of `exit` in
`main` ends the program without checking the `CERASTES_ENSURES` of `main`. (In these programs, which have no
input or output, a loop or recursion that never ends is undefined behaviour in
pass:[C++] anyway, which is why cerastes does not leave it unchecked.)

What a result rests on is the single-unit assumption above, and it includes
termination. A contract you declare for a function that is defined elsewhere
is trusted to hold *and to terminate*. This is most visible with a contract
that cannot be met:

[source,cpp]
----
include::example$verifying/trusted_never_returns.cpp[tag=source]
----

`absurd` verifies, because its only path calls a function that, by its
contract, never returns. If `never_returns` can in fact return, the
verification says nothing about `absurd`. A contract you declare for code you
have not verified is something you promise, not something the tool checks.

The termination assumption has a limit that the check cannot see. If a
function of this file calls a function that is defined in another file, which
in turn calls back a function of this file, the cycle goes through code that
was verified in another run: each file verifies, and the program does not
terminate. A recursion cycle that passes through a function defined in another
translation unit is not detected.

A parameter in a postcondition denotes the value it had on entry, as the
xref:annotations.adoc[Annotations] page describes. `CERASTES_CHECK` and a loop
invariant see its current value.

== Both modes mean the same

The same source means the same in C23 and in pass:[C++]20. Where the two
standards differ (conversions to a signed type, left shift of a negative
value), cerastes uses the stricter rule in both, so a `.c` file verifies, or
fails, identically in either mode:

[source,c]
----
include::example$verifying/same_in_both_modes.c[tag=source]
----

[#not-supported]
== What is not supported yet

cerastes rejects what it cannot verify, with a diagnostic at the line, and
never approximates it:

[source,cpp]
----
include::example$verifying/rejected_double.cpp[tag=source]
----

The constructs that are rejected in this version are:

* *Statements:* a `goto` that is not outward and forward (<<goto>>), the GNU
  computed `goto`, `try` and `throw`, `asm`, an `if` or
  `switch` with an init-statement or with a declaration in its condition, and the
  forms of `switch` listed in <<control-flow>>.
* *Declarations:* a `const` local with no initializer, a local initialized
  from itself (`int x = x;`), `static`, `thread_local` and
  `extern` locals, global variables other than the constants of <<constants>>,
  arrays, classes, unions,
  an enumeration declared in a function, a class or a template, or with a
  `bool` underlying type or an enumerator outside the range of `int`, an
  enumeration declared without its enumerators and without an underlying type,
  lambdas, templates, `constexpr` and `consteval` functions,
  variadic functions, function pointers, `CERASTES_REQUIRES` on `main`, a
  `main` declared not to return, and `CERASTES_ENSURES` on a function declared
  not to return.
* *Calls:* of a function with no body in the file and no contract, among them
  the functions of the C library other than `abort`, `exit` and `_Exit` (for
  example `quick_exit`, `+__builtin_trap+`, `+__builtin_unreachable+` and
  `std::terminate`).
* *Types:* pointers other than those xref:memory.adoc[Memory and ownership]
  describes (`void *`, `restrict` other than on a C parameter the contract owns,
  and pointers to structures, unions and functions are rejected, and so are
  pointer conversions other than adding `const` to the object pointed to; its
  xref:memory.adoc#not-yet[list] names the rest, such as `+owns(**pp)+`),
  references, arrays, floating point, `volatile`, `_BitInt`,
  vector types, enumerations declared in system headers. Array types, `_BitInt`,
  vector types and class templates with a constant argument
  (`std::array<char, 4>`) are rejected also as the operand of `sizeof`,
  `_Alignof`, `typeof` or `decltype` (`sizeof(int[3])`, `sizeof("abc")`): the
  compiler computes their size from a constant, which may have wrapped
  (`sizeof(char[65536u * 65536u + 1])` is 1). So is a typedef of an array type.
* *Expressions:* the bitwise shapes the compilers warn about
  (xref:integer-semantics.adoc#bitwise[Bitwise operators]), a character literal
  with more than one character or one that does not fit its type (`'ab'`,
  `L'ab'`), calls whose
  checks cannot be put in one order (<<calls>>: `100 / f(x) + 100 / g(y)`, two
  operands of `&&` or `||` with calls added together, an assignment in such an
  operand next to a check that depends on another call), the shapes of
  <<side-effects>> (an unsequenced
  modification, an assignment as a condition without extra parentheses, a comma
  operand without effect, a discarded value around a side effect, a side effect
  in `sizeof`, an assignment of a variable to itself), the value of a `?:` whose
  arms are `void`, the shapes of <<warning-shapes>>, and, in C, a variable named where a
  constant expression is required (a `case` value, `_Static_assert`, an
  enumerator's value), and an enumeration value that the compiler converts to an
  integer for arithmetic, a comparison of order, a unary operator, a shift or an
  arm of `?:` (comparing the order of two values of the same enumeration is
  allowed), a `?:` whose result is an enumeration (in C, a `?:` of enumerators
  compared with `==` or `!=`), a `switch` on an enumeration
  that the compilers' `-Wswitch` rejects (a `case` value that is not an
  enumerator, or a missing enumerator without `default`), in C an enumerator's value
  that names an earlier enumerator whose initializer has a type other than `int`
  (the front end gives it the pass:[C++] type) or that uses `sizeof` or `_Alignof`
  of an expression or `typeof`, and compound assignment,
  `pass:[++]` and `--` on an enumeration
  (xref:integer-semantics.adoc#enumerations[Enumerations]):
+
[source,c]
----
include::example$verifying/enum_arithmetic_rejected.c[tag=source]
----
* *Attributes:* any attribute other than the cerastes ones and `maybe_unused`,
  `nodiscard`, `deprecated`, `likely`, `unlikely`, `fallthrough` and `noreturn`
  (some attributes, such as `assume`, would let you state an unchecked fact).
* *Pragmas:* a `#pragma` the front end does not recognize (among them
  `#pragma clang attribute`, which applies attributes the verifier would not
  see, and `#pragma clang diagnostic` or `#pragma GCC diagnostic`), and the
  front end's own `#pragma diag_suppress` and its relatives, which could turn the
  errors cerastes relies on into warnings.

A function with a body but no contract is verified against the default
contract: its parameters and its result are in the range of their types.
