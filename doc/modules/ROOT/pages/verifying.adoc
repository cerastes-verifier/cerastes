= Verifying a program

`cerastes verify` checks a C or pass:[C++] source file against the contracts
written in it. It proves, for every function with a body, that the
postconditions hold, that every call meets the callee's precondition, that
every `CERASTES_CHECK` and loop invariant holds, that no integer
operation overflows, divides by zero or shifts out of range, and that every
loop and every recursive function terminates. When it cannot prove one of
these, it reports the line. This page describes the command,
what it verifies, what it prints and the assumptions a result rests on.

The annotations are described in xref:annotations.adoc[Annotations]. The
meaning of the integer operations is in xref:integer-semantics.adoc[Integer
semantics], and every message the tool can print is in
xref:error-messages.adoc[Error messages].

== Running it

[source,sh]
----
build/cerastes verify midpoint.cpp
----

The file is the one source file of the run. It is this function:

[source,cpp]
----
include::example$verifying/midpoint.cpp[tag=source]
----

[source,console]
----
midpoint.cpp: verified (1 function; one translation unit: assumes that functions defined elsewhere satisfy the contracts declared here)
----

The command takes these options and no others. An option that is not in this
table is refused with exit status 2, even if the front end would accept it:
verification must not depend on a diagnostic that was switched off or a
dialect that was changed behind its back.

[cols="2,5"]
|===
| Option | Meaning

| `-I<dir>`, `-I <dir>`
| Add `<dir>` to the user include path.

| `-D<name>[=<value>]`, `-U<name>`
| Define or undefine a macro. `+__CERASTES__+` is defined by the tool and cannot be
  defined or undefined. The names the annotations depend on
  (`+__has_cpp_attribute+`, `+__has_c_attribute+`, `cerastes`, `requires`,
  `+CERASTES_H+` and every `CERASTES_*` macro) are refused too.

| `--std=pass:[c++20]`, `--std=c23`
| The language mode. The default is `c23` for a `.c` file and `pass:[c++20]` for
  anything else. GNU dialects and C before C23 are not accepted.

| `--keep-vpr`, `--keep-vpr=<path>`
| Keep the generated Viper program and its position map. See
  <<keep-vpr>>.

| `--timeout=<seconds>`
| The wall-clock limit for the proof search. The default is 300. Reaching it is
  a failure of the tool, not a verdict on your program (exit status 3).

| `--help`, `--version`
| Print usage, or the version.
|===

The tools the verifier runs (the Java runtime, Silicon, Z3 and the system
include directories) are fixed when cerastes is built. Environment variables
such as `SILICON_JAR` or `Z3_EXE` do not change a result.

== What is verified

cerastes verifies the *primary file and every user header it includes*: each
function body in them. A header is verified again in every run that includes
it.

A *system file* is not verified. It is a file under one of the system include
directories the tool was built with (the SDK, the pass:[C++] library, the
compiler's own headers), or exactly the `include/cerastes.h` of the cerastes
checkout. The test is made on the file's real path (symbolic links and `..`
are resolved), never on a flag in the source, so a `#pragma` or a `#line` in
your code cannot turn the checks off. A `#line` directive in a verified file is
rejected for the same reason. A function declared in a system file is used only
through a contract; its body is never read.

A directory you give with `-I` is a user directory, even if it holds
library code.

The bodies of functions marked `CERASTES_PREDICATE` and `CERASTES_PURE` are
specification and are not verified. In this version a call of one of them in
executable code is rejected, and in a contract only `cerastes::old` may be
called.

== The output

A verification error is one line on standard output, followed by notes that
say which clause is involved:

[source,console]
----
midpoint_overflow.cpp:10: error: overflow: signed `int` addition may overflow
----

The file is written as you gave it on the command line (or as the include
resolved, for a header), the line is the line of the C or pass:[C++] source,
and the category is one of eleven names that
xref:error-messages.adoc[Error messages] explains. Errors are sorted by file,
then line, then category, and each is printed once. A program with errors
exits with status 1.

[source,cpp]
----
include::example$verifying/midpoint_overflow.cpp[tag=source]
----

A program that cerastes does not accept, because EDG finds a compile error
or because it uses a construct that cerastes does not verify, is reported
on standard error in EDG's format, with the diagnostic's name, and the exit
status is 2. Standard output is then empty:

[source,console]
----
"rejected_double.cpp", line 6: error #cerastes-unsupported_type: type "double" is not supported by "cerastes verify": only integer types and bool are (decision 0012)
  double half(double x)
         ^

1 error detected in the compilation of "rejected_double.cpp".
----

Nothing else is printed. In particular a warning from the front end in a
verified file is shown on standard error like any diagnostic, so a program
that is meant to verify cleanly should compile without warnings.

== Exit status

[cols="1,6"]
|===
| Status | Meaning

| 0 | Every function verified.
| 1 | Verification errors, printed on standard output.
| 2 | The program is not accepted: a front-end error, a construct cerastes does not verify, a refused option or a missing file.
| 3 | The tool failed: the prover crashed, timed out or gave no verdict, an error could not be traced to a source line, or the front end aborted with an internal error. This is never a statement about your program.
|===

== Loops and termination

A loop needs an invariant to be verified (the verifier does not unroll it) and
a *measure*, `CERASTES_DECREASES(...)`, to show that it ends. The invariant
must hold when the loop is first reached and after every iteration, and what
follows the loop is proved from the invariant and the negation of the
condition. The measure is one or more integer expressions that get smaller
with every iteration and never go below zero: in `n - i`, the loop condition
`i < n` makes it positive, and `i += 1` makes it smaller. The arithmetic in the
loop is checked on every iteration, and so is the condition each time it is
evaluated, and so is the arithmetic of the measure.

[source,cpp]
----
include::example$verifying/loop.cpp[tag=source]
----

Here the invariant `s == 2 * i` and the bound `i <= n` give `s == 2 * n` when
the loop ends, and the measure `n - i` shows that it ends. A loop with no
`CERASTES_INVARIANT` is verified with only the facts the verifier derives
automatically (that each variable the loop assigns stays in the range of its
type), which is rarely enough to prove anything about the result.

A recursive function needs a measure too, written after its parameter list. It
is compared from the entry of the function to every call of a function in the
same recursion cycle, over the arguments of the call:

[source,cpp]
----
include::example$verifying/recursion.cpp[tag=source]
----

A measure with several expressions is compared lexicographically: at the first
one that changes, the new value must be smaller than the old one, which must
not be negative, and the later ones may be anything. A function that is not in
a recursion cycle needs no measure. A loop, or a function in a cycle (direct
recursion, or mutual recursion through other functions of the file), without
one is rejected, because a program whose termination is not shown cannot be
called verified:

[source,cpp]
----
include::example$verifying/missing_measure.cpp[tag=source]
----

The errors a wrong invariant or measure can cause are `invariant-entry`,
`invariant-preserved` and `termination`, described in
xref:error-messages.adoc[Error messages].

[#control-flow]
== Leaving a loop early: break, continue, do and switch

`break` leaves a loop, or a `switch`, at once, without evaluating the loop's
condition, so the invariant is not checked there. What follows the loop is
proved from the way it was left: the invariant and the negated condition, or
the state at one of the `break` statements. `continue` ends the iteration: in a
`for` loop the increment runs, then the condition is evaluated again, so the
invariant and the measure are checked there as at the end of the body.

[source,c]
----
include::example$verifying/control_flow.c[tag=source]
----

In `smallest_divisor` the loop ends either at the `break`, where `n % d == 0`,
or when `d < n` is false, where the invariant gives `d == n`; both give the
postcondition.

A `do` loop runs its body before its first test, so its invariant holds at the
start of every iteration (on entry, and each time the test is true), and the
arithmetic of its condition is checked after the body, where the condition is
evaluated. `CERASTES_INVARIANT` and `CERASTES_DECREASES` are written before
`do`. A `do { ... } while (0)`, whose body runs once, needs no measure.

A `switch` evaluates its controlling expression once, with the usual checks,
and goes to the matching `case` label, to `default`, or past the `switch`.
Execution falls through from one label's statements to the next until a
`break`; `+[[fallthrough]];+` (or `+[[gnu::fallthrough]];+`) marks an intended
fallthrough for compilers that warn about it. Each `case` value is checked as it
is written, like any constant: `case 1 << 40:` is a `shift` error at the label,
even where the compiler only warns. cerastes rejects a `case` or `default` label that is not directly
inside the braces of its `switch` (as in Duff's device), a GNU case range
(`case 1 ... 3:`), a statement before the first label, a declaration that a
later label jumps over, and a `switch` with an init-statement or a declaration
in its condition.

[#goto]
== Jumping forward with goto

A `goto` is verified when it jumps *outward and forward*: its label is a later
statement of a block that encloses the `goto`, and no declaration of that block
lies between them. That covers the usual uses: an early exit to a common label
at the end of a function, a cleanup label, and leaving nested loops or a
`switch` at once. As with `break`, the loop's condition is not evaluated on the
way out, so its invariant is not checked there; after the label, what follows is
proved from each way of getting there.

[source,c]
----
include::example$verifying/goto_exit.c[tag=source]
----

After `done:`, the postcondition is proved for each way of getting there: from
either `goto`, where `result` is still -1, and from the subtraction, which
cannot overflow because `0 <= y <= x` holds there.

cerastes rejects a `goto` that jumps backward (write the loop as `while`, `for` or
`do`), one that jumps into a block, an `if` branch, a loop or the body of a
`switch`, one that jumps past a declaration that is still in scope at the label
(its variable would have no value there), and the GNU computed `goto`.

[#no-return]
== Functions that do not return

A function declared `+[[noreturn]]+` (or `_Noreturn` in C, or with the GNU
attribute `noreturn`) must never return: cerastes checks that no `return` and no
closing brace of its body can be reached, and reports one that can as a
`noreturn` error. A call of such a function ends the path of its caller, so what
would follow it is not checked.

`abort`, `exit` and `_Exit` from `<stdlib.h>` are known not to return. They are
the only functions of the C library that cerastes knows so far; `quick_exit`,
`+__builtin_trap+`, `+__builtin_unreachable+` (and C23's `unreachable()`) and
`std::terminate` are rejected.

[source,c]
----
include::example$verifying/no_return.c[tag=source]
----

Without the call of `fail`, `a / b` would be a `division-by-zero` and an
`overflow` error. A function declared not to return cannot have
`CERASTES_ENSURES` (it would never be checked), and `main` cannot be declared not
to return. A function that never returns by looping forever is rejected, since
every loop needs a measure.

[#assert]
== assert

`assert(e)` from `<assert.h>` (or `<cassert>`) is verified as a check of `e`: a
failure is a `check` error at the `assert`. Unlike `CERASTES_CHECK`, it is code:
`e` is evaluated at run time, so its arithmetic is checked like any expression's,
and it may call functions. When `NDEBUG` is defined, `assert` does nothing, and
cerastes checks nothing, as the program will run. A result holds for the
configuration that was verified: with asserts on, the code after `assert(e)` may
rely on `e`, which a build with `NDEBUG` no longer checks, so verify the
configuration you ship.

[source,c]
----
include::example$verifying/assert.c[tag=source]
----

Here the `requires` keeps `sum` small, the `assert` states a bound that the `requires` guarantees, and the contract pins the result exactly: `r == (a + b) / 2`.

[#keep-vpr]
== Keeping the Viper program

cerastes translates the program to Viper, the verification language of the
Silicon prover, and Silicon asks Z3. `--keep-vpr` writes the Viper text and
the position map that links each checked line of it to your source:

[source,sh]
----
build/cerastes verify midpoint.cpp --keep-vpr
----

This writes `midpoint.vpr` and `midpoint.vpr.map` into the current directory.
`--keep-vpr=<path>` writes `<path>` and `<path>.map`. The files are written for
every run that reaches the prover (exit status 0, 1 or 3), whatever the
verdict. They are for people who want to see what was checked; the reports
already point at your source, never at the Viper file.

== The single-unit assumption

A result is for one translation unit. A contract you declare for a function
that is defined elsewhere, in another source file or in a library, is
*trusted*: the callers in this unit are verified against it, and nothing here
checks that the definition satisfies it. The success line says so. The
definition is checked when the file that contains it is verified; a library
function that is never verified is trusted for good.

[source,cpp]
----
include::example$verifying/declared_elsewhere.cpp[tag=source]
----

Here `two_ids` is verified assuming `next_id` meets its contract. A function
that has neither a contract nor a body in a verified file cannot be called from
verified code: the call is rejected, because there is nothing to verify it
against.

== What a result means

A verified function terminates on every input that satisfies its `requires`,
has no undefined behaviour on the way, and returns a value that satisfies its
`ensures`, or ends the program by calling a function that does not return (such
as `abort` or `exit`): the result is *total correctness*. A call of `exit` in
`main` ends the program without checking the `CERASTES_ENSURES` of `main`. (In these programs, which have no
input or output, a loop or recursion that never ends is undefined behaviour in
pass:[C++] anyway, which is why cerastes does not leave it unchecked.)

What a result rests on is the single-unit assumption above, and it includes
termination. A contract you declare for a function that is defined elsewhere
is trusted to hold *and to terminate*. This is most visible with a contract
that cannot be met:

[source,cpp]
----
include::example$verifying/trusted_never_returns.cpp[tag=source]
----

`absurd` verifies, because its only path calls a function that, by its
contract, never returns. If `never_returns` can in fact return, the
verification says nothing about `absurd`. A contract you declare for code you
have not verified is something you promise, not something the tool checks.

The termination assumption has a limit that the check cannot see. If a
function of this file calls a function that is defined in another file, which
in turn calls back a function of this file, the cycle goes through code that
was verified in another run: each file verifies, and the program does not
terminate. A recursion cycle that passes through a function defined in another
translation unit is not detected.

A parameter in a postcondition denotes the value it had on entry, as the
xref:annotations.adoc[Annotations] page describes. `CERASTES_CHECK` and a loop
invariant see its current value.

== Both modes mean the same

The same source means the same in C23 and in pass:[C++]20. Where the two
standards differ (conversions to a signed type, left shift of a negative
value), cerastes uses the stricter rule in both, so a `.c` file verifies, or
fails, identically in either mode:

[source,c]
----

[#not-supported]
== What is not supported yet

cerastes rejects what it cannot verify, with a diagnostic at the line, and
never approximates it:

[source,cpp]
----
include::example$verifying/rejected_double.cpp[tag=source]
----

The constructs that are rejected in this version are:

* *Statements:* a `goto` that is not outward and forward (<<goto>>), the GNU
  computed `goto`, `try` and `throw`, `asm`, an `if` or
  `switch` with an init-statement or with a declaration in its condition, and the
  forms of `switch` listed in <<control-flow>>.
* *Declarations:* a local with no initializer, `static`, `thread_local` and
  `extern` locals, global variables (also `const` ones), arrays, classes, unions,
  enumerations, lambdas, templates, `constexpr` and `consteval` functions,
  variadic functions, function pointers, `CERASTES_REQUIRES` on `main`, a
  `main` declared not to return, and `CERASTES_ENSURES` on a function declared
  not to return.
* *Calls:* of a function with no body in the file and no contract, among them
  the functions of the C library other than `abort`, `exit` and `_Exit` (for
  example `quick_exit`, `+__builtin_trap+`, `+__builtin_unreachable+` and
  `std::terminate`).
* *Types:* pointers, references, floating point, `volatile`, `_BitInt`, vector
  types.
* *Expressions:* the bitwise operators (`&`, `|`, `^`, `~`), the comma
  operator, an assignment used as a value, two calls in one expression that are
  not nested in each other (`f(x) + g(y)`), and a call in the second operand of
  `&&`, `||` or `?:`, or in a loop condition.
* *Attributes:* any attribute other than the cerastes ones and `maybe_unused`,
  `nodiscard`, `deprecated`, `likely`, `unlikely`, `fallthrough` and `noreturn`
  (some attributes, such as `assume`, would let you state an unchecked fact).

A function with a body but no contract is verified against the default
contract: its parameters and its result are in the range of their types.
