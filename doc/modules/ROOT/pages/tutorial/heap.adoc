= The heap

Memory from `malloc` is the hardest kind to get right in C. An allocation can
fail, it must be freed exactly once, and only by someone who owns it, and every
allocation must be freed. cerastes proves all of these. This chapter allocates a
single object, hands it from one function to another, and shows the three
mistakes cerastes catches.

== An allocation and its owner

[source,c]
----
include::example$tutorial/heap_cell.c[tag=source]
----

[source,console]
----
heap_cell.c: verified (3 functions; one translation unit: assumes that functions defined elsewhere satisfy the contracts declared here)
----

`malloc` can return `NULL`, and `make_cell` tests for it before it writes.
`cerastes_owns_block(r)` in its postcondition hands the whole allocation to
the caller: everything `free` needs, not just the right to read and write
`*r`. `drop_cell` takes it back with the same words in its precondition and
frees it. `main` tests the result, uses it, and passes it on.

`malloc` and `free` get their contracts from vlibc, the C library contracts
cerastes is built with. An allocation is one object of the type the result is
converted to, at once: `(int *)malloc(sizeof(int))`.

== Forgetting the null test

Leave out the test in `make_cell`, and the write may go through a null
pointer:

[source,c]
----
include::example$tutorial/heap_cell_no_null_test_error.c[tag=source]
----

[source,console]
----
heap_cell_no_null_test_error.c:13: error: null-dereference: dereferences `p`, which may be null
----

== Forgetting to free

A function that still owns an allocation when it returns, and does not hand it
to its caller, has lost it for good. That is a `leak`, reported at the closing
brace, and `main` is no exception:

[source,c]
----
include::example$tutorial/heap_cell_no_free_error.c[tag=source]
----

[source,console]
----
heap_cell_no_free_error.c:34: error: leak: `main` may return while it still owns an allocation that its `ensures` does not hand back
----

== Freeing twice

After `free`, the allocation is gone and nobody owns it. Hand it to `drop_cell`
a second time:

[source,c]
----
include::example$tutorial/heap_cell_double_free_error.c[tag=source]
----

[source,console]
----
heap_cell_double_free_error.c:34: error: permission: calls `drop_cell`, which needs to own the whole allocation `p` points to, without owning it
----

The second `drop_cell(p)` asks for the whole allocation, and `main` gave it
away in the first call: a `permission` error at the call. Two calls of `free(p)`
in one function are reported as `invalid-free` at the second one, since the
allocation may already be freed.

== An owner you cannot forget

A function that allocates and frees in the same place can mark the variable that
holds the allocation `CERASTES_OWNING`. The variable then owns the block, and
cerastes checks that it no longer does when the variable's scope ends:

[source,c]
----
include::example$tutorial/heap_owner.c[tag=source]
----

[source,console]
----
heap_owner.c: verified (1 function; one translation unit: assumes that functions defined elsewhere satisfy the contracts declared here)
----

`round_trip` frees `p` before it returns on the path where the allocation
succeeded, and returns without allocating on the other. Add a path that returns
early and forgets the `free`, and cerastes reports it where the variable's scope
ends, at the `return` that leaves it, instead of at the end of the function:

[source,c]
----
include::example$tutorial/heap_owner_leak_error.c[tag=source]
----

[source,console]
----
heap_owner_leak_error.c:18: error: leak: owning `p` still holds its block
----

The same words appear when the variable is assigned a new allocation while it
holds one. A variable that is not marked is checked at the end of the function
only, which is why this chapter's earlier leak is reported at the closing brace.

== An owner that outlives a call

A global can own an allocation too. `cerastes::owning` on a global says that the
block it points to belongs to it across calls. So a function whose contract
names the global with `cerastes_owns(g)` receives that block with it, and must give
back a global that is null or holds a whole block:

[source,c]
----
include::example$tutorial/heap_global_owner.c[tag=source]
----

`main` calls `install` twice: the second call frees the first block before it
allocates another. `main` then returns while `g` still holds its block. That is not a
leak: a global owner may keep its block for the whole program. A function that frees
the block and forgets to reset the global is reported at its return:

[source,c]
----
include::example$tutorial/heap_global_owner_error.c[tag=source]
----

[source,console]
----
heap_global_owner_error.c:16: error: permission: returns while owning global `g` does not hold its block: set it to `NULL` after freeing it
----

== A structure that owns its buffer

A structure can own an allocation through one of its members. `CERASTES_OWNING` on
the member `data` says that the block it points to belongs to the structure. So
whoever owns the structure owns the buffer too: `buf_make` hands both to its caller
(its result is `owning`), and `buf_destroy`, which takes the structure's block,
takes the buffer with it, without saying so in its contract:

[source,c]
----
include::example$tutorial/heap_owning_field.c[tag=source]
----

A destructor must therefore free the buffer before the structure. One that frees
only the structure still holds the buffer when it returns, and nothing else can
free it:

[source,c]
----
include::example$tutorial/heap_owning_field_error.c[tag=source]
----

[source,console]
----
heap_owning_field_error.c:33: error: leak: `buf_destroy` may return while it still owns an allocation that its `ensures` does not hand back
----

A function that borrows the structure with `cerastes_owns(*b)` borrows the buffer
too, and may free it and store a new one, but a pointer it stores into the member
must be null or a whole allocation it holds.

That freedom has a price for the caller. A pointer taken into the buffer before the
call, `int *t = b->data;`, may not be used after it, because the callee may have
replaced the block. A function that promises not to replace it says so with
`CERASTES_NOT_INVALIDATING` on the parameter: whatever the contract takes through the
parameter comes back, and the pointer to the buffer is unchanged. `bump` below does,
and `use` writes through `t` after the call (xref:annotations.adoc#not-invalidating[The
not_invalidating marker] has the rules, and what the verifier checks about the body):

== What you have learned

* The result of `malloc` must be tested against `NULL` before it is used.
* `cerastes_owns_block(p)` is ownership of a whole allocation; a contract uses
  it to hand an allocation to the caller or to take one.
* Every allocation is freed exactly once by its owner; one that is not is a
  `leak`, at the end of the function that loses it.
* A local marked `CERASTES_OWNING` owns its allocation, and a path that leaves
  its scope while it still holds the block is a `leak` at that path.
* A global marked `CERASTES_OWNING` owns its allocation across calls: a contract's
  `cerastes_owns(g)` carries the block with it, and `main` may end while it holds one.
* A member marked `CERASTES_OWNING` owns its allocation for its structure: whoever
  owns the structure owns the buffer, and a destructor frees both.
* A parameter marked `CERASTES_NOT_INVALIDATING` leaves the buffers it borrows in
  place, so a caller's pointer into one stays valid across the call.
