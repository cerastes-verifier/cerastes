= Memory and ownership

This page says what cerastes proves about programs that use pointers. For every
access through a pointer it proves that the access is defined: the pointer is
not null, the object it points to still exists, and the function has the right
to read or write it. A use of a pointer whose object has ended is an error too,
even when nothing is read through it, as C and pass:[C++] say.

This version covers pointers to integers, `bool` and enumerations: in local
variables, as parameters and as results, with contracts that say which objects
a function may read or write (<<contracts>>), in loops (<<loops>>) and across
jumps (<<leaving>>). <<not-yet>> lists what is still rejected.

== Objects whose address is taken

A local variable whose address is never taken is a plain value, as before. A
local whose address is taken anywhere in the function (`&x`) is an *object in
memory*: it exists from the moment its block is entered until the block ends,
and it is reached by name or through any pointer to it. Reading or writing it
through a pointer is the same as reading or writing it by name:

[source,c]
----
include::example$memory/pointer_to_local.c[tag=source]
----

Each object starts without a value unless its declaration has an initializer,
and reading it first is reported as
xref:error-messages.adoc#_uninitialized[`uninitialized`], whether the read is by
name or through a pointer. Arithmetic through a pointer is checked like any
other (xref:integer-semantics.adoc[Integer semantics]): `pass:[(*p)++]` overflows
exactly when `pass:[x++]` would.

== Null pointers

A null pointer is written `NULL`, `0` or `nullptr`, in C and in pass:[C++]. A
pointer that may be null must not be dereferenced: such a read or write is
reported as xref:error-messages.adoc#_null_dereference[`null-dereference`].
Testing the pointer first is enough, since cerastes follows the paths of the
program:

[source,c]
----
include::example$memory/null_guarded.c[tag=source]
----

A pointer used as a condition (`if (p)`, `!p`, `p && …`) means `p != NULL`.

== Comparing pointers

`==` and `!=` compare pointers as C does: two pointers to different objects are
never equal, and a pointer to an object is never null. `CERASTES_CHECK` and
`assert` may use pointers like the code around them:

[source,c]
----
include::example$memory/address_comparison.c[tag=source]
----

Comparisons of order (`<`, `>`), arithmetic on pointers and conversions between
pointer types are not supported yet.

A pointer may also point *one past the end* of an object, and C does not say
whether such a pointer equals a pointer to another object that happens to follow
it in memory. So when `==` or `!=` compares two pointers that may point into
different objects, one of them one past its end, cerastes reports
xref:error-messages.adoc#_pointer_comparison[`pointer-comparison`] instead of
choosing an answer. Inside one function this cannot happen; a pointer parameter
can (<<contracts>>).

== Lifetimes and dangling pointers

An object in memory ends when its block ends. After that, a pointer to it is
*dangling*: reading or writing through it is reported as
xref:error-messages.adoc#_permission[`permission`], and any other use of its
value, even a test, a comparison or a copy, is reported as
xref:error-messages.adoc#_lifetime[`lifetime`], because C and pass:[C++] make
the value of such a pointer indeterminate:

[source,c]
----
include::example$memory/dangling_pointer.c[tag=source]
----

Returning the address of a local variable or a parameter (`return &x;`, also
through parentheses, a cast, either arm of `?:` or the right operand of `,`) is
rejected, as clang's `-Wreturn-stack-address` and GCC's `-Wreturn-local-addr`
warn about it: the object ends as the function returns
(xref:verifying.adoc#warning-shapes[Shapes the compilers warn about]). A copy of
such an address returned through a variable (`int *p = &x; return p;`) is
reported where the caller first uses it, as
xref:error-messages.adoc#_lifetime[`lifetime`].

[#contracts]
== Pointer parameters and contracts

A function that takes a pointer says in its contract what it may do with the
object the pointer points to. Three specification functions, from `<cerastes.h>`,
state it; in C they are spelled `cerastes_owns`, `cerastes_reads` and
`cerastes_live`, in pass:[C++] also `cerastes::owns`, `cerastes::reads` and
`cerastes::live` (the C spelling works in both, so a header shared by C and
pass:[C++] writes one):

[cols="2,5"]
|===
| Written | Means

| `cerastes_owns(*p)`
| `p` is not null and points to an object that exists, holds a value, and that
the function may read and write; in `ensures`, the function gives it back

| `cerastes_reads(*p)`
| the same, but the function may only read the object; others may read it too

| `cerastes_live(p)`
| `p` is not null and points into an object that exists; the function may
compare and copy `p` but not read through it
|===

The caller must hold what the callee's `requires` asks for, at the call, and the
callee must hold what its `ensures` promises, at every `return`; either failure
is reported as xref:error-messages.adoc#_permission[`permission`]. Whatever the
caller holds that the callee's contract does not name keeps its value across
the call. `cerastes_old(*p)` (in pass:[C++] also `cerastes::old(*p)`) in an
`ensures` is the value `*p` had when the function was entered:

[source,c]
----
include::example$memory/pointer_parameter.c[tag=source]
----

A function that only reads takes `cerastes_reads`: the caller lends it the
right to read and can write the object again as soon as the call returns, and
two `reads` of the same object may be passed to one call:

[source,c]
----
include::example$memory/reads_parameter.c[tag=source]
----

A pointer that may be null is described by a condition, `p == NULL ||
cerastes_owns(*p)`, and the function tests it before it dereferences `p`:

[source,c]
----
include::example$memory/null_or_owned.c[tag=source]
----

A few more rules:

* A contract may read `*p` only where an `owns` or `reads` of `*p` comes before
  it, on that path; otherwise the contract itself is reported as
  xref:error-messages.adoc#_permission[`permission`] ("the contract of `f` reads
  `*p` without owning it"). In an `ensures`, `*p` is the value when the function
  returns, so the `ensures` needs its own `owns` or `reads` of `*p`;
  `cerastes_old(*p)` needs the one in `requires`.
* Returning or comparing a pointer parameter uses its value, so the contract must
  say that its object exists: `cerastes_live(p)`, or an `owns` or `reads` of `*p`.
  A pointer result may be related to the parameters (`ensures(r, r == p || r ==
  q)`).
* A function that takes `cerastes_owns(*p)` in its `requires` and does not give
  it back in its `ensures` keeps the object. If that object is a local variable
  of the caller, the caller cannot end its lifetime: the closing brace of the
  variable's block is reported as xref:error-messages.adoc#_lifetime[`lifetime`].
* In C, a `restrict` pointer parameter is accepted when the contract owns its
  object and gives it back: owning it already means that nothing else reaches
  the object during the call, which is what `restrict` promises.
* The address of a parameter may be taken (`int *q = &a;`): the parameter is
  then an object in memory, like a local.
* A contract may own an object on one path and only read it on another
  (`c ? cerastes_owns(*p) : cerastes_reads(*p)`), but not do both on one path,
  and its `ensures` may give back only what its `requires` took on the same
  path; either mistake is reported at the contract as
  xref:error-messages.adoc#_permission[`permission`], even for a function whose
  body is elsewhere:
+
[source,c]
----
include::example$memory/conditional_ownership.c[tag=source]
----
* A function's `decreases` may read an object its `requires` owns or reads; it
  is compared, as for integers, between the function's entry and each recursive
  call:
+
[source,c]
----
include::example$memory/measure_over_memory.c[tag=source]
----
* Verification time grows quickly with the number of pointer parameters of
  one type that only `reads` or `live` describe, since any of them may point to
  the same object: four take a few seconds, five tens of seconds, and six or
  more may reach the time limit (an error, never a wrong answer).

[#expressions]
== Writes and calls inside expressions

An object in memory may be written inside an expression, as a variable can
(xref:verifying.adoc#side-effects[Side effects in expressions]): `y = pass:[x++]`,
`f(*p = 1)` and `pass:[(*p)++] + 1` are fine, and so is a call of a function whose
contract owns or reads an object, next to other uses of objects in memory:

[source,c]
----
include::example$memory/expression_write.c[tag=source]
----

C does not say in which order the operands of most operators are evaluated. Two
accesses to one object without a sequence point between them, one of them a
write, are undefined behaviour, and a call next to an access to an object that
the call may change gives a result that depends on an order C leaves open. When
the source names the object twice (`pass:[x++] + x`, `*p = pass:[(*p)++]`), the compilers
warn and cerastes rejects the expression
(xref:verifying.adoc#side-effects[`unsequenced_modification`]). When it names it
in two ways that may meet (`*p = pass:[(*q)++]`, `x + bump(&x)`, `bump(p) + peek(q)`),
cerastes checks, on each path, that they are different objects, and reports
xref:error-messages.adoc#_unsequenced[`unsequenced`] where they may not be:

[source,c]
----
include::example$memory/call_beside.c[tag=source]
----

A call and the accesses written in its own arguments, a statement's own
assignment of the call's result (`x = bump(&x);`), and accesses separated by `,`,
`&&`, `||` or the condition of `?:` have a fixed order, and are not reported.

[#loops]
== Loops

A loop may use pointers and objects in memory like any other code. Its body
gets, without any annotation, every object in memory the function holds when
the loop starts: the local variables whose address is taken (in every block
that is open there, including those declared later in it), the parameters whose
address is taken, and the object each pointer parameter points to, when the
function never assigns that parameter. As for a local variable that the loop
assigns, the loop's invariant states what the loop does to their values:

[source,c]
----
include::example$memory/loop_through_pointer.c[tag=source]
----

What the invariant does not state is known in two cases only:

* An object keeps its value across the loop when no write in the loop can reach
  it: no assignment to it by name, no write through a pointer to its type, and
  no call of a function whose contract owns an object of its type. A write
  through a pointer counts against every object of that type, since cerastes does
  not follow where each pointer points:
+
[source,c]
----
include::example$memory/loop_havoc.c[tag=source]
----
+
cerastes reports the `ensures` of `havoc`: the write through `pl` may have
changed `keep`. Stating the value in the invariant is enough:
+
[source,c]
----
include::example$memory/loop_havoc_fixed.c[tag=source]
----
* An object that held a value when the loop started still holds one. An object
  that the loop gives its first value is known to hold one after the loop only
  when the invariant states its value (`i == 0 || x == i`); an invariant that
  reads an object that holds no value yet is reported as
  xref:error-messages.adoc#_uninitialized[`uninitialized`].

Every iteration must end holding what the loop started with: a function called
in the loop that keeps one of these objects is reported as
xref:error-messages.adoc#_permission[`permission`] at the closing brace of the
loop's body. An invariant or a measure may read objects in memory
(`CERASTES_INVARIANT(x == i)`, `CERASTES_DECREASES(*p)`), compare pointers and
take addresses; it reads only what the loop holds, and an invariant that reads
an object the loop does not hold is reported as
xref:error-messages.adoc#_permission[`permission`]. A pointer that the loop
assigns needs an invariant saying where it points (`p == &x || p == &y`). The
address of a variable in an annotation (`p == &x`) is accepted only when the
code takes that address too.

A pointer parameter that the function assigns does not take its object into
loops yet: using that object inside a loop, or returning from inside a loop when
the `ensures` gives it back, is reported as
xref:error-messages.adoc#_permission[`permission`].

[#leaving]
== Leaving a block

`break`, `continue`, `goto` and `return` end the lifetime of every object in
memory whose block they leave, as the closing brace does. A function that kept
such an object is reported at the jump as

[#not-yet]
== What is not supported yet

These are rejected with a diagnostic, never approximated
(xref:verifying.adoc#not-supported[the full list]):

* a pointer to a pointer, and the address of a pointer variable;
* `owns`, `reads` or a value through a pointer result (`*r`), and contracts
  that name objects other than those the parameters point to;
* `owns`, `reads` and `live` in a loop invariant;
* `restrict` except on a C parameter whose contract owns its object;
* `void *`, and pointers to structures, unions and functions;
* conversions between pointer types other than adding `const`, comparisons of
  order and arithmetic on pointers.

In C, the compiler's warnings about pointers of incompatible types
(`long *q = &i;` for an `int i`) are errors under `cerastes verify`.
