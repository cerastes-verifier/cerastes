= Memory and ownership

This page says what cerastes proves about programs that use pointers. For every
access through a pointer it proves that the access is defined: the pointer is
not null, the object it points to still exists, and the function has the right
to read or write it. A use of a pointer whose object has ended is an error too,
even when nothing is read through it, as C and pass:[C++] say.

This version covers pointers to integers, `bool` and enumerations, and
pointers to such pointers (<<pointers-to-pointers>>): in local variables, as
parameters and as results, with contracts that say which objects
a function may read or write (<<contracts>>), in loops (<<loops>>) and across
jumps (<<leaving>>); global and `static` local variables (<<globals>>,
<<static-locals>>); and memory from `malloc`, `calloc` and `free` (<<heap>>).
<<not-yet>> lists what is still rejected.

== Objects whose address is taken

A local variable whose address is never taken is a plain value, as before. A
local whose address is taken anywhere in the function (`&x`) is an *object in
memory*: it exists from the moment its block is entered until the block ends,
and it is reached by name or through any pointer to it. Reading or writing it
through a pointer is the same as reading or writing it by name:

[source,c]
----
include::example$memory/pointer_to_local.c[tag=source]
----

Each object starts without a value unless its declaration has an initializer,
and reading it first is reported as
xref:error-messages.adoc#_uninitialized[`uninitialized`], whether the read is by
name or through a pointer. Arithmetic through a pointer is checked like any
other (xref:integer-semantics.adoc[Integer semantics]): `pass:[(*p)++]` overflows
exactly when `pass:[x++]` would.

== Null pointers

A null pointer is written `NULL`, `0` or `nullptr`, in C and in pass:[C++]. A
pointer that may be null must not be dereferenced: such a read or write is
reported as xref:error-messages.adoc#_null_dereference[`null-dereference`].
Testing the pointer first is enough, since cerastes follows the paths of the
program:

[source,c]
----
include::example$memory/null_guarded.c[tag=source]
----

A pointer used as a condition (`if (p)`, `!p`, `p && …`) means `p != NULL`.

== Comparing pointers

`==` and `!=` compare pointers as C does: two pointers to different objects are
never equal, and a pointer to an object is never null. `CERASTES_CHECK` and
`assert` may use pointers like the code around them:

[source,c]
----
include::example$memory/address_comparison.c[tag=source]
----

Comparisons of order (`<`, `>`) and arithmetic on pointers are not supported
yet, nor conversions between pointer types other than adding `const` to the
object pointed to (<<pointers-to-pointers>>).

A pointer may also point *one past the end* of an object, and C does not say
whether such a pointer equals a pointer to another object that happens to follow
it in memory. So when `==` or `!=` compares two pointers that may point into
different objects, one of them one past its end, cerastes reports
xref:error-messages.adoc#_pointer_comparison[`pointer-comparison`] instead of
choosing an answer. Inside one function this cannot happen; a pointer parameter
can (<<contracts>>).

== Lifetimes and dangling pointers

An object in memory ends when its block ends. After that, a pointer to it is
*dangling*: reading or writing through it is reported as
xref:error-messages.adoc#_permission[`permission`], and any other use of its
value, even a test, a comparison or a copy, is reported as
xref:error-messages.adoc#_lifetime[`lifetime`], because C and pass:[C++] make
the value of such a pointer indeterminate:

[source,c]
----
include::example$memory/dangling_pointer.c[tag=source]
----

Returning the address of a local variable or a parameter (`return &x;`, also
through parentheses, a cast, either arm of `?:` or the right operand of `,`) is
rejected, as clang's `-Wreturn-stack-address` and GCC's `-Wreturn-local-addr`
warn about it: the object ends as the function returns
(xref:verifying.adoc#warning-shapes[Shapes the compilers warn about]). A copy of
such an address returned through a variable (`int *p = &x; return p;`) is
reported where the caller first uses it, as
xref:error-messages.adoc#_lifetime[`lifetime`].

[#pointers-to-pointers]
== Pointers to pointers

A pointer variable whose address is taken is an object in memory like any
other, so pointers to pointers (`+int **+`, and deeper) follow the same rules:
`*pp` reads or writes the pointer that `pp` points to, `+**pp+` the object that
pointer points to, and each step is checked:

[source,c]
----
include::example$memory/pointer_to_pointer.c[tag=source]
----

Writing `*pp` changes where `p` points. When the pointer stored in `*pp` is
dangling, reading or writing `+**pp+` is reported as
xref:error-messages.adoc#_permission[`permission`] and any other use of `*pp`
as xref:error-messages.adoc#_lifetime[`lifetime`], as for any pointer. In a
loop, a write through a pointer to a pointer may change every pointer of that
type, as a write through an `int *` may change every `int` (<<loops>>).

A conversion may add `const` to the object a pointer points to (`+int **+` to
`int *const *`), but not further down. `+int **+` to `+const int **+` would let a
`const` object be written through the original pointer, so it is rejected even
when written as a cast, which compilers accept without a warning; `+int **+` to
`const int *const *`, which pass:[C++] allows and C does not, is rejected in
both languages for now.

Two uses of one such object that C does not order, one of them a write
(`pass:[**pp + (**pp = 1)]`, `(*pp = &y) == *pp`), are rejected, as GCC's
`-Wsequence-point` warns about them
(xref:verifying.adoc#side-effects[Side effects in expressions]).

A contract can name every object along the way. `cerastes_owns(*pp)` holds the
pointer `pp` points to; `+cerastes_owns(**pp)+` (or `+cerastes_reads(**pp)+`)
holds the object that pointer points to, and `cerastes_live(*pp)` says only that
it points to a live object. An atom reached through a pointer read needs an
earlier atom that holds that pointer: `+cerastes_owns(**pp)+` needs
`cerastes_owns(*pp)` or `cerastes_reads(*pp)` before it, or the contract is
reported as reading `*pp` without owning it:

[source,c]
----
include::example$memory/pointer_to_pointer_contract.c[tag=source]
----

In a `requires`, `+**pp+` is the object `*pp` points to on entry; in an
`ensures`, the one it points to on return. A function that may change `*pp`
says whether it did: `*pp == cerastes_old(*pp)` when it does not, or names the
new object. `+cerastes_old(**pp)+` is the value, on entry, of the object `*pp`
pointed to on entry. A function may move `*pp` to another object it was given
and promise `+cerastes_owns(**pp)+` for it; a function declared without a body
must say which object its `ensures` names (`*pp == cerastes_old(*pp)`, or
`*pp == q` for an object it was given), since nothing checks such a contract
against code. The same holds at any depth (`+***ppp+`) and through a pointer
member (`+p->q->x+`, <<structures>>) or a pointer global (`+*gp+`,
<<globals>>).

[#contracts]
== Pointer parameters and contracts

A function that takes a pointer says in its contract what it may do with the
object the pointer points to. Three specification functions, from `<cerastes.h>`,
state it; in C they are spelled `cerastes_owns`, `cerastes_reads` and
`cerastes_live`, in pass:[C++] also `cerastes::owns`, `cerastes::reads` and
`cerastes::live` (the C spelling works in both, so a header shared by C and
pass:[C++] writes one):

[cols="2,5"]
|===
| Written | Means

| `cerastes_owns(*p)`
| `p` is not null and points to an object that exists, holds a value, and that
the function may read and write; in `ensures`, the function gives it back

| `cerastes_reads(*p)`
| the same, but the function may only read the object; others may read it too

| `cerastes_live(p)`
| `p` is not null and points into an object that exists; the function may
compare and copy `p` but not read through it
|===

The caller must hold what the callee's `requires` asks for, at the call, and the
callee must hold what its `ensures` promises, at every `return`; either failure
is reported as xref:error-messages.adoc#_permission[`permission`]. Whatever the
caller holds that the callee's contract does not name keeps its value across
the call. `cerastes_old(*p)` (in pass:[C++] also `cerastes::old(*p)`) in an
`ensures` is the value `*p` had when the function was entered:

[source,c]
----
include::example$memory/pointer_parameter.c[tag=source]
----

A function that only reads takes `cerastes_reads`: the caller lends it the
right to read and can write the object again as soon as the call returns, and
two `reads` of the same object may be passed to one call:

[source,c]
----
include::example$memory/reads_parameter.c[tag=source]
----

A pointer that may be null is described by a condition, `p == NULL ||
cerastes_owns(*p)`, and the function tests it before it dereferences `p`:

[source,c]
----
include::example$memory/null_or_owned.c[tag=source]
----

The attribute `cerastes::owning` on a pointer parameter (or `CERASTES_OWNING`, a macro
that other compilers read as nothing) says the same in one word: the parameter
may be null, and when it is not, the function owns its object and gives it back,
exactly as `p == NULL || cerastes_owns(*p)` in both the `requires` and the
`ensures` would. The attribute goes before the parameter's declaration or after
its name, and the contract's other clauses may read `*p` where `p != NULL`:

[source,c]
----
include::example$memory/owning_parameter.c[tag=source]
----

Beside the attribute, an explicit `cerastes_owns(*p)` (which also says that `p`
is not null) or `p == NULL || cerastes_owns(*p)` takes the attribute's place in
its clause list; `cerastes_reads(*p)`, `cerastes_live(p)` or an `owns` under
another condition is rejected. Every declaration of the function carries the
same `owning` attributes, on the same parameters.

A few more rules:

* A contract may read `*p` only where an `owns` or `reads` of `*p` comes before
  it, on that path; otherwise the contract itself is reported as
  xref:error-messages.adoc#_permission[`permission`] ("the contract of `f` reads
  `*p` without owning it"). In an `ensures`, `*p` is the value when the function
  returns, so the `ensures` needs its own `owns` or `reads` of `*p`;
  `cerastes_old(*p)` needs the one in `requires`.
* Returning or comparing a pointer parameter uses its value, so the contract must
  say that its object exists: `cerastes_live(p)`, or an `owns` or `reads` of `*p`.
  A pointer result may be related to the parameters (`ensures(r, r == p || r ==
  q)`), and its object read as `*r` where an `owns` or `reads` of that object
  comes before it (`ensures(r, r == p && cerastes_owns(*p) && *r == 0)`).
* A parameter of type `+int **+` may own the pointer it points to
  (`cerastes_owns(*pp)`), say where that pointer points (`*pp == q`,
  `cerastes_old(*pp)`), and own, read or require the liveness of the object
  behind it (`+cerastes_owns(**pp)+`, `cerastes_live(*pp)`;
  <<pointers-to-pointers>>). A guard may read through a pointer too:
  `+*pp == NULL || cerastes_owns(**pp)+`, after an atom that holds `*pp`.
* A contract may not compare pointers whose objects differ in `const`
  (`r == v` for `int *r` and `const int *v`, or `*pp == v`), nor convert a
  pointer to one whose object differs in `const` (`(const int *)r`), nor own an
  object it reaches through a pointer to `const` (`cerastes_owns(*v)` for
  `const int *v`; a function that only reads it takes `cerastes_reads(*v)`).
  Otherwise a function whose body is elsewhere could hand its caller a pointer
  through which a `const` object is written, or write one itself, which C leaves
  undefined. Each is rejected.
* A function that takes `cerastes_owns(*p)` in its `requires` and does not give
  it back in its `ensures` keeps the object. If that object is a local variable
  of the caller, the caller cannot end its lifetime: the closing brace of the
  variable's block is reported as xref:error-messages.adoc#_lifetime[`lifetime`].
* In C, a `restrict` pointer parameter is accepted when the contract owns its
  object and gives it back: owning it already means that nothing else reaches
  the object during the call, which is what `restrict` promises. It is rejected
  when another parameter, or a global the contract names, could hold a pointer
  of the same type (a pointer to a pointer, a structure with a pointer member,
  a pointer global): a pointer read from there is not based on the `restrict`
  one, and the compilers may assume it never reaches the same object.
* The address of a parameter may be taken (`int *q = &a;`): the parameter is
  then an object in memory, like a local.
* A contract may own an object on one path and only read it on another
  (`c ? cerastes_owns(*p) : cerastes_reads(*p)`), but not do both on one path,
  and its `ensures` may give back only what its `requires` took on the same
  path; either mistake is reported at the contract as
  xref:error-messages.adoc#_permission[`permission`], even for a function whose
  body is elsewhere:
+
[source,c]
----
include::example$memory/conditional_ownership.c[tag=source]
----
* A function's `decreases` may read an object its `requires` owns or reads; it
  is compared, as for integers, between the function's entry and each recursive
  call:
+
[source,c]
----
include::example$memory/measure_over_memory.c[tag=source]
----
* Verification time grows quickly with the number of pointer parameters of
  one type that only `reads` or `live` describe, since any of them may point to
  the same object: four take a few seconds, five tens of seconds, and six or
  more may reach the time limit (an error, never a wrong answer).

[#initialization]
== Initialization through pointers

A pointer parameter whose contract owns its object (`cerastes_owns(*p)`) expects an
object that has a value: the caller gives it one, and the function returns it with
one. An argument whose object may not have a value yet is reported at the call as
xref:error-messages.adoc#_uninitialized[`uninitialized`] ("passes `&x` to `set`, whose
parameter `p` needs `*p` to have a value; it may not have one here"); the same holds
for `cerastes_reads(*p)`.

Two attributes from the pass:[C++] initialization profile (P4222), in the
`cerastes::` spelling, let a function receive an object that has no value yet:

* `cerastes::must_init` (the macro `CERASTES_MUST_INIT`): the object may have no
  value on entry, and the function gives it one before it returns. A path that
  returns without writing `*p` is reported as
  xref:error-messages.adoc#_postcondition[`postcondition`] ("returns without
  initializing `*p`, which `cerastes::must_init` on `p` promises"). After the call
  the caller may read the object, and the `ensures` may say what it holds.
* `cerastes::ref_to_uninit` (the macro `CERASTES_REF_TO_UNINIT`): the object may
  have no value on entry, and the function promises nothing about it on return,
  except that an object that had a value still has one (its value may have changed).

[source,c]
----
include::example$memory/init_must_init.c[tag=source]
----

[source,c]
----
include::example$memory/init_ref_to_uninit.c[tag=source]
----

The rules:

* The attribute goes before the parameter's declaration or after its name, on a
  pointer to an object that is not `const` (a `+int **+` parameter's object is the
  pointer it points to). Its contract owns the object: `cerastes_owns(*p)` in the
  `requires`, or `cerastes::owning`, and for `must_init` in the `ensures` too.
  `cerastes_reads(*p)` beside either attribute is rejected, and so are both
  attributes on one parameter. Every declaration of the function carries the same
  attributes on the same parameters.
* Inside the function, `*p` is read only after it is written, on every path, as a
  local without an initializer is (xref:verifying.adoc#uninitialized[Locals without
  an initializer]).
* The contract may not read the object where it may have no value: `*p` in the
  `requires`, `cerastes_old(*p)`, `*p` in a `decreases`, and `*p` in the `ensures`
  of a `ref_to_uninit` parameter are rejected; the `ensures` of a `must_init`
  parameter may read it (`*p == 0` above). A read through another pointer that may
  equal `p` is reported at the contract as
  xref:error-messages.adoc#_permission[`permission`].
* A `must_init` parameter that the function writes only inside a loop is reported,
  even when the loop always runs: give it a value before the loop.
* The attributes are rejected on a function that never returns (`must_init`), on a
  `pure` or `predicate` function, and on a redeclaration of a function a system
  header declares.

`cerastes::uninit` (the macro `CERASTES_UNINIT`) on a local without an initializer
states that it starts without a value, and the option `--strict-init` asks for it on
every such local and for these attributes wherever an object without a value is
passed (xref:verifying.adoc#strict-init[The strict initialization mode]).

[#structures]
== Structures

A structure whose members are integers, `bool`, enumerations, pointers and other
such structures can be a local, the object a pointer points to, and the subject
of a contract. Each member is an object of its own: `pt.x` and `pt.y` are
different objects, and `&pt.x` points to `pt.x` only. A structure local is
created without a value when it has no initializer; a braced initializer gives
every member a value, zero for the members it does not name. A member is read,
written, and passed by address like any other object:

[source,c]
----
include::example$memory/struct_local.c[tag=source]
----

`cerastes_owns(*p)` of a pointer to a structure owns every member, and
`cerastes_old(+p->x+)` is the value a member had on entry. A function that swaps
two members passes their addresses on, which is VeriFast's `point_mirror`:

[source,c]
----
include::example$memory/struct_parameter.c[tag=source]
----

A contract may also name one member, `cerastes_owns(+p->count+)` or
`cerastes_reads(+p->count+)`: the callee then may touch that member only, and
the caller keeps the others with their values:

[source,c]
----
include::example$memory/struct_member_owns.c[tag=source]
----

Separation is decided by the objects two parameters can reach, whatever their
types: a pointer to a structure and a pointer to an `int` reach one object when
the `int` is one of the structure's members. Passing `&pt` and `&pt.x` to two
owning parameters is reported as
xref:error-messages.adoc#_permission[`permission`] at the call:

[source,c]
----
include::example$memory/struct_overlap.c[tag=source]
----

Copying a structure (`t = s;`, `+*p = *q;+`, `struct point t = s;`) reads every
member: a member without a value is reported as
xref:error-messages.adoc#_uninitialized[`uninitialized`] at the copy, even
though C lets a partly initialized structure be copied. A copy is a statement or
an initializer; its value cannot be used (`(t = s).x` is rejected). In C a
structure's initializer is evaluated before the object has a value, so
`struct point pt = {1, pt.x};` reads `pt.x` without a value; in pass:[C++] the
members are initialized in order.

The markers of <<initialization>> work on structures: `cerastes::uninit` on a
structure local, and `cerastes::ref_to_uninit` and `cerastes::must_init` on a
pointer to a structure, where `must_init` promises every member.

*Passing and returning structures.* A structure can be passed and returned by
value. In a contract a parameter's members (`p.x`) are their values on entry,
like any parameter, and a result's members are named through the result
(`r.x`); a member of a call's result is read directly (`make(4, 0).y`):

[source,c]
----
include::example$memory/struct_by_value.c[tag=source]
----

Passing or returning a structure copies it, so every member must have a value:
a member without one is reported as
xref:error-messages.adoc#_uninitialized[`uninitialized`] at the call or the
`return`, as at a copy. A contract reads a structure value only member by member
(`p == q` and `cerastes_old(p)` are rejected: C has no `==` on structures).

A contract can follow a pointer member: `+cerastes_owns(p->q->x)+` names the
member `x` of the object `p->q` points to (after an atom that holds `p->q`, such
as `cerastes_owns(*p)`), `+cerastes_owns(*s.q)+` and `+cerastes_live(s.q)+` the
object a by-value parameter's pointer member points to, and in an `ensures`
`+*r.q+` the object a returned structure's pointer member points to, after an
atom on that object (`+r.q == p && cerastes_owns(*p) && *r.q == 1+`). Without
`+cerastes_live(s.q)+` a function cannot use the member's value (`return s.q;` is
reported as xref:error-messages.adoc#_lifetime[`lifetime`]):

[source,c]
----
include::example$memory/struct_pointer_member.c[tag=source]
----

`+cerastes_live(r.q)+` and `+cerastes_owns(*r.q)+` of a returned structure are not
supported yet: they hand the caller something the function's `requires` did not
take.

*Compound literals.* In C, `(struct point){1, 2}` is a value wherever a structure
value is: an initializer, an assignment, an argument, a returned value.
`&(struct point){1, 2}` (and `+&(int){5}+`) is the address of an object that lives
until the end of the block the literal is in, like a local declared there: after
the block a pointer to it is dangling (<<_lifetimes_and_dangling_pointers>>):

[source,c]
----
include::example$memory/compound_literal.c[tag=source]
----

The elements of a compound literal are evaluated before any member is stored,
in no particular order, as the elements of an initializer are. In pass:[C++],
where compound literals are a compiler extension creating temporaries, they are
accepted as values only, and so are `S{1, 2}` and `S()`.

Not supported yet, each rejected with a diagnostic: unions, bit-fields, array
members, `const`, `volatile` and `_Atomic` members, anonymous members, members
that are `void *` or pointers to functions, `packed` structures, structures
from system headers (such as `FILE`), structures defined inside a function, and
in pass:[C++] every class feature beyond a C structure (member functions,
constructors, base classes, access control, `static` members, default member
initializers). Passing or returning a structure by value, structure globals,
initializers that elide the braces of an inner structure
(`struct line l = {1, 2, 3, 4};`) and, in C, designators out of declaration
order are rejected too, and so are a structure `?:`, comma or assignment used as
a value (`t = c ? a : b;`), the address of a `const` compound literal, a compound
literal in a loop's condition or step, and a compound literal used as an object
without `&` (`(struct point){1, 2}.x = 3;`).

[#globals]
== Global variables

A global variable that is not `const` is an object in memory that exists for
the whole run of the program. `main` starts with every global of the file, each
holding its initial value; any other function reaches a global only through its
contract, which names it the way it names `*p`: `cerastes_owns(count)` to read
and write it, `cerastes_reads(count)` to read it. A function whose contract does
not name a global cannot change it, so its caller keeps the global's value
across the call. A function that reads or writes a global its contract does not
name is reported as xref:error-messages.adoc#_permission[`permission`]:

[source,c]
----
include::example$memory/global_variable.c[tag=source]
----

`cerastes_old(count)` in an `ensures` is the global's value when the function
was entered, and a contract may compare a pointer with its address
(`r == &count`). The address of a global can be taken, stored and passed like
the address of a local (`int *p = &count;`); it never dangles.

*Initial values.* `main` knows a global's initial value when the file is the
only one that can set it:

* a global declared `static` (or, in pass:[C++], in an unnamed namespace) starts
  with its initializer's value, `0` or a null pointer without one;
* in C, so does any global with an initializer;
* a C global without an initializer and not `static` (`int count;`) starts with an
  unknown value, since another file may define it with a value (compilers that
  merge such definitions, `-fcommon`, are the default on macOS);
* in pass:[C++], a global that is not `static` starts with an unknown value,
  since another file's initialization may change it before `main` runs, and so
  does a global whose address is the initial value of such a global.

The rest of the program is assumed to keep to this file's contracts: code that
runs before `main` in another file calls none of this file's functions, and a
function of another file declared here changes only what its contract names
(xref:verifying.adoc#one-unit[one translation unit]). A structure global
follows the same rules member by member: each member starts with the
initializer's value, zero (or null) for the members it does not name, and a
contract names the whole object (`cerastes_owns(stats)`) or one member
(`+cerastes_owns(stats.hits)+`):

[source,c]
----
include::example$memory/struct_global.c[tag=source]
----

A contract can name the object a pointer global points to,
`+cerastes_owns(*gp)+`, after an atom that holds the global itself
(`cerastes_owns(gp)` or `cerastes_reads(gp)`):

[source,c]
----
include::example$memory/pointer_global_target.c[tag=source]
----

Globals of other files (`extern int count;` with no definition here) and arrays
are not supported yet, nor is a structure global initialized with the address of
another global's member (`&h.x`).

[#static-locals]
== `static` local variables

A `static` local variable is a global whose name only its function sees, so no
contract can name it. cerastes gives the function the right to it implicitly,
and the same right to every function that calls it, directly or not; `main`
holds it from the start. Its initializer runs once, before `main`, and nothing
is known about its value when the function is entered, since another call may
have changed it:

[source,c]
----
include::example$memory/static_local.c[tag=source]
----

Since every caller holds the variable across the call, two calls that both
reach the function and that C does not order (`next_id() + next_id()`) are
reported as xref:error-messages.adoc#_unsequenced[`unsequenced`]: the result
depends on which runs first. A `static` local may be a structure; the function
and its callers then hold every member. A function may return the address of its
`static` local; its caller can use the pointer when the contract says what it
points to (<<results,Results that give a place>>), and otherwise a use of it is
reported as xref:error-messages.adoc#_lifetime[`lifetime`]. A `static const`
local is not supported yet.

[#results]
== Results that give a place

An `ensures` that names a pointer parameter's object normally gives back what the
`requires` took (<<contracts,Pointer parameters and contracts>>). A function can
also promise something about the object its pointer result points to, or about a
member of a returned structure's pointer (`cerastes_owns(*r)`,
`cerastes_reads(*r)`, `cerastes_live(r)`, `cerastes_live(r.q)`,

of two kinds, and cerastes decides which at each `return`.

object and uses the right it holds. With `live(r)` the caller may use the
pointer: copy it, compare it, pass it on.

== Writes and calls inside expressions

An object in memory may be written inside an expression, as a variable can
(xref:verifying.adoc#side-effects[Side effects in expressions]): `y = pass:[x++]`,
`f(*p = 1)` and `pass:[(*p)++] + 1` are fine, and so is a call of a function whose
contract owns or reads an object, next to other uses of objects in memory:

[source,c]
----

C does not say in which order the operands of most operators are evaluated. Two
accesses to one object without a sequence point between them, one of them a
write, are undefined behaviour, and a call next to an access to an object that
the call may change gives a result that depends on an order C leaves open. When
the source names the object twice (`pass:[x++] + x`, `*p = pass:[(*p)++]`), the compilers
warn and cerastes rejects the expression
(xref:verifying.adoc#side-effects[`unsequenced_modification`]). When it names it
in two ways that may meet (`*p = pass:[(*q)++]`, `x + bump(&x)`, `bump(p) + peek(q)`),
cerastes checks, on each path, that they are different objects, and reports
xref:error-messages.adoc#_unsequenced[`unsequenced`] where they may not be:

[source,c]

----

A call and the accesses written in its own arguments, a statement's own
assignment of the call's result (`x = bump(&x);`), and accesses separated by `,`,
`&&`, `||` or the condition of `?:` have a fixed order, and are not reported.

[#loops]
== Loops

A loop may use pointers and objects in memory like any other code. Its body
gets, without any annotation, every object in memory the function holds when
the loop starts: the local variables whose address is taken (in every block
that is open there, including those declared later in it), the parameters whose
address is taken, the object each pointer parameter points to, when the
function never assigns that parameter, and every object the contract names
through a pointer read (`+**pp+`, `+*gp+`, `+p->q->x+`, `+*s.q+`): the object the
`requires` named, and, when the function may change the pointer before the loop,
also the object the pointer points to when the loop starts. As for a local
variable that the loop assigns, the loop's invariant states what the loop does
to their values:

* An object keeps its value across the loop when no write in the loop can reach
  it: no assignment to it by name, no write through a pointer to its type, and
  no call of a function whose contract owns an object of its type. A write
  through a pointer counts against every object of that type, since cerastes does
  not follow where each pointer points:
+

----
+

changed `keep`. Stating the value in the invariant is enough:
+

----

----
* An object that held a value when the loop started still holds one. An object
  that the loop gives its first value is known to hold one after the loop only
  when the invariant states its value (`i == 0 || x == i`); an invariant that
  reads an object that holds no value yet is reported as
  xref:error-messages.adoc#_uninitialized[`uninitialized`].

Every iteration must end holding what the loop started with: a function called
in the loop that keeps one of these objects is reported as
xref:error-messages.adoc#_permission[`permission`] at the closing brace of the
loop's body. An invariant or a measure may read objects in memory
(`CERASTES_INVARIANT(x == i)`, `CERASTES_DECREASES(*p)`), compare pointers and
take addresses; it reads only what the loop holds, and an invariant that reads
an object the loop does not hold is reported as
xref:error-messages.adoc#_permission[`permission`]. A pointer that the loop
assigns needs an invariant saying where it points (`p == &x || p == &y`). The
address of a variable in an annotation (`p == &x`) is accepted only when the
code takes that address too.

A pointer that the function assigns (a pointer local, or a parameter it
reassigns) takes nothing into a loop by itself. The invariant says what the loop
holds through it, with `cerastes_owns(*q)`, `cerastes_reads(*q)` or
`cerastes_live(q)` as in a contract, also through a pointer read
(`+cerastes_owns(**pp)+`, `+cerastes_owns(*p->q)+`, `+cerastes_owns(*gp)+`, and
`cerastes_owns(*q)` where the address of `q` itself is taken): the loop must hold it when it starts and at
the end of every iteration, and gives it back after the loop. Without it, an
access inside the loop is reported as
xref:error-messages.adoc#_permission[`permission`]:

xref:error-messages.adoc#_permission[`permission`], at the invariant when the
loop starts without it, and at the closing brace of the body when an iteration
ends without it. When the loop moves such a pointer
(`q = &y;`), the invariant must also say where it may point

[#heap]
== Allocated memory: `malloc`, `calloc` and `free`

`malloc`, `calloc` and `free` come with contracts in
xref:verifying.adoc#vlibc[vlibc], cerastes's C library headers. An
allocation is a new object that the function now owns entirely; `free` ends it.
cerastes proves that every allocation is tested against null before it is used,
that only what was allocated is freed, and only once, and that nothing allocated
is forgotten (a _leak_).

*One object per allocation.* In this version an allocation holds one object: its
size must be `sizeof(T)` (`sizeof *p` is the same), and its result must be
converted at once to `T *`: in an initializer or assignment
(`int *p = malloc(sizeof *p);`, C), a `return`, an argument, or a cast
(`(int *)malloc(sizeof(int))`, which pass:[C++] needs). The object then has
type `T` for its whole life. `calloc(1, sizeof(T))` gives an object whose
members are all zero, null for a pointer member; the object from `malloc` has no
value until the program gives it one (reading it first is
xref:error-messages.adoc#_uninitialized[`uninitialized`]). Arrays of objects
(`n * sizeof(T)`) and `realloc` are planned with arrays.

[source,c]
----
include::example$memory/heap_struct.c[tag=source]
----

*Freeing.* `free(p)` needs the whole allocation that `p` points to the start
of. Freeing it twice, freeing a local or global object or a structure's member,
freeing an object the function only borrows, or freeing while a function it
called may still hold a pointer to it is
xref:error-messages.adoc#_invalid_free[`invalid-free`]. After `free(p)`, any use
of `p` is xref:error-messages.adoc#_lifetime[`lifetime`] and any access through
it xref:error-messages.adoc#_permission[`permission`]. `free(NULL)` does nothing,
but it must be written with a typed pointer: a bare `free(NULL)` is rejected.

*Leaks.* A function that ends while it still owns an allocation it does not hand
to its caller is reported at its closing brace as
xref:error-messages.adoc#_leak[`leak`], and so is `main` (as VeriFast does): free
everything before `main` returns. A path that ends in `exit`, `abort` or
`_Exit` is not checked, since it does not return. An iteration of a loop that
ends while it owns an allocation the loop does not carry to the next iteration
is a leak too, reported at the end of the loop's body.

*Loops.* A loop may use an allocation made before it, through a pointer variable
declared before the loop: the loop keeps the allocation as it found it, and may
read, write or free it. When the loop moves allocations between pointers (two
pointers swapped, a pointer given a new allocation), the allocation is no longer
the one it found, and the loop's invariant says which pointer holds one:
`CERASTES_INVARIANT(p == NULL || cerastes_owns_block(p))` keeps the whole
allocation `p` points to, whichever it is, at the start of every iteration. Two
such pointers in one invariant name two different allocations.

[source,c]
----
include::example$memory/heap_loop_swap_invariant.c[tag=source]
----

Without the invariant, the swap is reported: after the loop nothing says which
variable holds which allocation. An owning local
(<<owning-locals,below>>) needs no such invariant, since the loop keeps its block
by its value.

*Handing an allocation over.* `cerastes_owns_block(p)` (`cerastes::owns_block`
in pass:[C++]) in a contract is ownership of the whole allocation `p` points to
the start of, everything `free` needs. In a `requires` alone, the function takes
the allocation (it frees it, or hands it on); in an `ensures` about the result,
the caller receives it; in both, about a parameter, the function borrows it and
gives it back. `cerastes::owning` written on a function means the same as
`ensures(r == NULL || owns_block(r))`, and `cerastes::ref_to_uninit` on such a
function says the caller receives an object without a value, as from `malloc`:

[source,c]
----
include::example$memory/heap_cell.c[tag=source]
----

[#blocks-through-memory]
*Through a pointer or a global.* The pointer that `cerastes_owns_block` takes may
also be read from memory:

* `cerastes_owns_block(*pp)` is the allocation `+*pp+` points to the start of;
* `cerastes_owns_block(p->next)` is the one a member points to;
* `cerastes_owns_block(g)` is the one a global pointer points to.

The pointer itself must be owned or read earlier in the same clause list
(`cerastes_owns(*pp) && cerastes_owns_block(*pp)`), as every read in a contract
must. In a `requires` it names the allocation the pointer holds when the function
is called; in an `ensures`, the one it holds when the function returns. So a
function can allocate into `+*pp+` and hand the allocation to its caller:

[source,c]
----

----

Nothing checks what a function without a body in the program returns. So when
such a function borrows an allocation through a pointer or a global, its contract
must say that it gives back the same one (`+*pp == cerastes_old(*pp)+`). A function
without a body that takes or hands over an allocation through a pointer or a
global is rejected: that needs the contracts of other translation units, which
are planned. A local that owns an allocation is
<<owning-locals,an owning local>>, and a global that does is
<<owning-globals,an owning global>>.

*vlibc's allocator.* vlibc also has an allocator of its own,

the library `libvlibc` (xref:verifying.adoc#vlibc[vlibc]). The first three have
the contracts of `malloc`, `calloc` and `free`, and cerastes checks their calls
the same way. Its blocks are a heap of their own: a block from `vlibc_malloc`
or `vlibc_calloc` is freed with `vlibc_free`, a block from `malloc` or `calloc`
with `free`, and freeing a block with the other allocator's function is

objects only in the storage `std::malloc` and its family return (placement `new`
comes with classes).

[#vlibc-blocks]
*A vlibc block in a contract.* `cerastes_owns_block` and `cerastes::owning` name a

[#owning-locals]
== Owning locals

A pointer local marked `cerastes::owning` (`CERASTES_OWNING`) owns the allocation
it points to. cerastes then reports a forgotten allocation where it happens, at
the end of the variable's scope or when the variable is assigned another value,
instead of only at the end of the function
(xref:annotations.adoc#marked-locals[the attribute]).

*The value rule.* An owner is given the start of an allocation the function
holds whole, or null. Anything else (the address of a local, a pointer into the
middle of a block, a block the function does not own) is

passed to another owner or returned. One that still holds it is

an owner sets the variable to `NULL` after the `free`, and its invariant says so:
the loop cannot carry "freed" otherwise. A loop that allocates into the variable
every iteration, without freeing the previous block, drops a block in the second
iteration (the reassignment rule above). So an owner that the loop allocates into
must be `NULL` at the head of each iteration: say so in the invariant

that the owner holds nothing there.

allocator, so a vlibc loop may start from a `NULL` owner; an owner that enters
the loop with a block of the other allocator is `permission` at the loop's entry,
even when the loop would free it before the first assignment.

[#owning-globals]
== Owning globals and `static` locals

A global or a `static` local marked `cerastes::owning` holds the block it points
to across calls. It starts null. An owning global with external linkage in
pass:[C++], or a C global declared without an initializer, starts with a value
cerastes cannot know: another translation unit may set it. So `main` must assign
such a global before it hands it on. Its initializer, when it has one, must be a
null pointer.

*Who holds it.* A function that names `cerastes_owns(g)` of an owning global in
its contract also receives and returns the block `g` points to, when `g` is not
null. It is as if the contract said `cerastes_owns(g) && (g == NULL ||
cerastes_owns_block(g))`. So when the function returns, `g` is null or holds
a whole block the function holds. `cerastes_reads(g)` gives only the pointer's
value. A `static` local's block travels the same way, through the implicit
`owns` of the `static` local that its function and every caller already have:

[source,c]
----
include::example$memory/owning_global.c[tag=source]
----

*Assigning it.* As for an owning local, a block that the global already holds
must be freed or handed on before the global is assigned another value
(xref:error-messages.adoc#_leak[`leak`] at the assignment). The value it receives
must be null or the start of a block the function holds whole
(xref:error-messages.adoc#_permission[`permission`]). A function that frees the
block and returns while `g` still points to it is `permission` at the return: set
`g` to `NULL` after freeing it.

[source,c]
----
include::example$memory/owning_global_return_after_free.c[tag=source]
----

*The end of `main`.* `main` may return while an owning global or `static` local
still holds its block. An owner with static storage keeps its object for the
whole program, as P4417R0 allows. A block that only a global without
`cerastes::owning` points to is still a `leak` when `main` returns.

*Owning locals whose address is taken.* An owning local whose address is taken is
an owner like any other. A write through a pointer to it is a write to the owner,
checked like an assignment. A function that receives its address decides by its
contract what happens to the block: with `cerastes_owns(*pp)` alone it may change
the pointer, and with `cerastes_owns(*pp) && (*pp == NULL ||
cerastes_owns_block(*pp))` in both lists it borrows the block too.

[#owning-fields]
== Owning fields

A pointer member of a structure marked `cerastes::owning` owns the block it points
to, for as long as the structure does: a structure that owns its buffer. Whoever
owns the structure owns the buffer too, so a contract that says
`cerastes_owns(*b)` of a `struct buf *b` gives and takes the block `b->data`
points to whenever it is not null, as if it also said `b->data == NULL ||
cerastes_owns_block(b->data)`. You do not write that clause; cerastes adds it
after every `owns` that covers the member (`cerastes_owns(*b)`, an `owns` of an
enclosing member, of the member itself, or of a structure global), after an
`owning` parameter's and result's block, and after `cerastes_owns_block(b)`. A
member whose pointee is itself a structure with owning members adds their blocks
too, to any depth, as long as no structure owns itself:

[source,c]
----
include::example$memory/owning_field.c[tag=source]
----

`buf_init` is the initializer: its `requires` gives the structure without values
(`CERASTES_MUST_INIT`), which owns nothing yet, and its `ensures` gives back a
structure whose member is null or holds a whole block. `buf_put` borrows the
structure and its block, and may replace the block. `buf_destroy` takes the
structure's block and, through its member, the buffer: it must free both.
`cerastes_reads(*b)` gives the member's value and nothing it owns; a function
that reads the buffer writes `cerastes_reads(*b->data)` beside it. The attribute
goes on a pointer to an object, in either position (`int *data
CERASTES_OWNING;` or `[[cerastes::owning]] int *data;`), on each declarator that
owns.

*Storing into the member.* The value stored must be null or the start of a block
the function holds whole, or the store is
xref:error-messages.adoc#_permission[`permission`]:

[source,c]
----
include::example$memory/owning_field_store_error.c[tag=source]
----

A block the member held when it is overwritten, or when the structure is freed,
is not reported at that line: cerastes cannot tell, for a structure reached
through a pointer, whether another owner took the block first. The function
still holds it, so it is a xref:error-messages.adoc#_leak[`leak`] at the
function's last line ("may return while it still owns an allocation that its
`ensures` does not hand back"), or at a loop's back edge if it happens in a
loop:

[source,c]
----
include::example$memory/owning_field_drop_error.c[tag=source]
----

*A structure in a variable.* An owning member of a local structure, of a global
structure or of a `static` local structure is an owner like an owning variable
(<<owning-locals>>, <<owning-globals>>). Assigning to it while it holds a block
is a `leak` at the assignment, and a local structure whose member still holds a
block when its lifetime ends is a `leak` there ("owning field `s.data` still holds
its block"). A function given `&s` decides by its
contract, as for `&v`: with `cerastes_owns(*b)` it borrows the structure and the
block, and may replace it.

[source,c]
----

----

[source,c]
----

----

`main` may end while a structure global or a `static` local structure still
holds blocks through its owning members, and through theirs: as for an owning
global, an owner with static storage keeps its object for the whole program.

[source,c]
----

----

*Copies.* Copying a structure (`t = s;`, `*q = *p;`, `struct buf t = *p;`) copies
its members, and each owning member of the copy is a store to an owner: the
copy and the original then hold the same block, as two owning variables do after
`b = a;`. One of them must be set to `NULL` before both are handed to a function
or returned, and a function that only reads the original (`cerastes_reads(*p)`)
cannot copy it into an owner. A structure passed or returned by value owns
nothing unless its contract says so (`s.data == NULL ||
cerastes_owns_block(s.data)`).

[source,c]
----
include::example$memory/owning_field_copy.c[tag=source]
----

*Loops.* A loop invariant `cerastes_owns(*b)` carries the member's block too, so
a loop may free and replace it on every iteration:

[source,c]
----
include::example$memory/owning_field_loop.c[tag=source]
----

Each owning member's block in a loop invariant costs time, and two of them in one
loop take minutes; a loop that replaces two members' blocks verifies, but
slowly.

*When a loop needs its invariant written.* cerastes carries an owning member's
block through a loop by itself when the loop works on the structure through what
holds it: a local or global structure, an owning pointer, or a parameter whose
structure the invariant owns. Two kinds of loop need a fact that only the program
knows, and the invariant states it:

* a loop that replaces the member's block through a second, non-owning pointer to
  a structure the function borrows (`v = p`). The invariant owns the structure
  through the parameter, `cerastes_owns(*p)`; owning it through the second pointer,
  `cerastes_owns(*v)`, is reported (`v->data` may be `+p->data+`), and without the
  invariant the loop's frees are reported:
+
[source,c]
----
include::example$memory/owning_field_loop_alias.c[tag=source]
----
* a loop that frees an owning pointer and gives it a new structure on every
  iteration, but frees the member's block only in its first iteration. That is a
  fact of one iteration, which only a written invariant can state:
  `CERASTES_INVARIANT(v == NULL || i != 0 || v->data == NULL ||
  cerastes_owns_block(v->data))`. Where the owning pointer's address is taken
  (`pv = &v`), this invariant cannot be written yet, and the loop is reported
  although it is correct.

A function whose contract consumes the structure's cells (`requires` owns
`+**pp+`, `ensures` owns only `+*pp+`) leaves the caller without the structure,
inside a loop or not: a second call, or a free of what `+*pp+` points to, is reported.

*The buffer must hold values.* Where a contract owns the structure, the member's
block must hold values, as every block a contract owns must: a structure whose
buffer was allocated but not yet written cannot be passed to `buf_put` (an
`uninitialized` error at the call). Write the buffer first.

=== P4417R0's owners in cerastes

P4417R0's invalidation profile marks owners with `[[owner]]`. In cerastes:

[cols="1,1"]
|===
|P4417R0 |cerastes

|`[[owner]]` on a local variable, a global or a `static` local
|`cerastes::owning` (<<owning-locals>>, <<owning-globals>>)

|`[[owner]]` on a member
|`cerastes::owning` (this section)

|`[[owner]]` on a result
|`cerastes::owning` on the function (<<heap>>)

|`[[owner]]` on a parameter: the callee takes the object and must delete it
|`CERASTES_REQUIRES(p == NULL \|\| cerastes_owns_block(p))` with no `ensures` about `p`

|(no attribute: a borrow)
|`cerastes::owning` on a parameter, which lends the block for the call

|a static owner need not delete its object
|`main` may end while a static owner holds its block

|raw storage (`malloc`, `free`) is outside the profile

|`[[not_invalidating]]` on a pointer parameter

  (xref:annotations.adoc#not-invalidating[The not_invalidating marker])

|p4: an owning result must initialize an owner, be assigned to one, be returned by a

[#block-guards]
== A block that depends on memory

`cerastes_owns_block(p)` may be under a condition, as the atoms of an `owns` and a
`reads` may: `cond ? cerastes_owns_block(p) : true`, or `p == NULL || ...`. The
condition may read memory, in the state the clause is about: a `requires` reads it
on entry, an `ensures` on return. The function below takes the block exactly where
`*q` is positive, and frees it under the same test:

[source,c]
----

----

An `ensures` guard decides whether the caller receives a block, and is read on
return, so the caller learns the block only where the guard holds after the call:

[source,c]
----

----

A function that borrows a block under a guard and gives it back under the same
guard must say that the guard still holds on return: `*q == cerastes_old(*q)`,
or use a guard that cannot change. The `ensures` guard is read on return, so
without it the contract itself is wrong, whatever the body does: on a path where
`*q` is no longer positive it returns a block that the `requires` did not take,
which is `permission`, reported at the contract:

guard reads (here `*q`), like any contract read.

[#not-yet]
== What is not supported yet

These are rejected with a diagnostic, never approximated
(xref:verifying.adoc#not-supported[the full list]):

* contracts that name objects other than those reached from the parameters, the
  global variables and the result, and, in a function whose body is not in the
  file, an `owns`, `reads`, `live` or `cerastes_owns_block` that its `requires`
  does not take, except on the result and only where no clause equates the
  result with anything but a null pointer (nothing verifies the contract, so it
  may promise only what the caller cannot already hold: the contract manifest,
  planned with the concepts);
* `cerastes_old` inside the path of a place (`+*cerastes_old(*pp)+`, the object
  `*pp` pointed to on entry, read on return; `+cerastes_old(p)->q->x+`), and
  `cerastes_old` in a loop invariant (copy the value into a local before the
  loop);
* globals defined in another file, `volatile`, `_Atomic`, `const` structure and
  thread-local globals, `static const` locals, and global arrays;
* the structure features listed in <<structures>>;
* `owns`, `reads` and `live` in a `do … while (0)` invariant or a measure, and of
  a global itself in an invariant (`cerastes_owns(g)`: the loop holds it
  already);
* a structure that owns itself through its owning members (`struct node { struct
  node *next CERASTES_OWNING; }`, or two structures that own each other: a list,
  planned with recursive predicates), `cerastes::ref_to_uninit` on a member and on
  a pointer to a structure with an owning member (planned for the next version),
  an owning member that is not a pointer to an object, and a function without a
  body in the file that hands over a new structure whose owning members hold
  blocks, other than a pointer with `cerastes_owns(*r)` whose structure owns one
  block (<<owning-fields>>);
* an owning or marked global, `static` local or owning member whose initializer is
  not a null pointer, and `owning(n)`;
* a function that returns the address of a `static` local structure on some paths
  and a new structure whose owning member holds a block on others is reported as a
  `leak`;
* some loops over owning members are reported although they are correct: a loop
  that frees and replaces an owning pointer whose address is taken (`pv = &v`), if it
  also frees the member's block (the invariant it needs cannot be written yet,
  <<owning-fields>>); a loop in `main` that hands a global structure to a function
  through a pointer it holds in a variable (`pg = &g`); a loop that may replace an
  owning global pointer, or store into a global structure through a pointer to it,
  and frees an owning member's block; and a loop over a chain of owning members that
  also writes an unrelated variable whose address is taken, or whose middle owner it
  frees and sets to null (`i == 0 || a.b == NULL` in its invariant does not help
  yet); and a loop that copies a whole structure holding an owning member beside an
  integer member, reported as `uninitialized` at the end of an iteration;
* `cerastes::uninit` on anything but a local, and `cerastes::must_init` on
  anything but a parameter (P4222 defines it for parameters only);
* the attributes of the P4417R0 and P4418R0 invalidation profile that are not
  taken over: `cerastes::not_invalidating` on a function (the profile's member
  function form; the front end refuses it, and a member function is
  planned with the classes) and `no_dangling`. An owner parameter that transfers its
  object to the callee is the contract `requires(p == NULL || cerastes_owns_block(p))`,
  and there is no suppression for a pointer that dangles on purpose: cerastes proves
  or reports each use;
* allocations of more than one object (`n * sizeof(T)`) and `realloc` (<<heap>>);
* in a function whose body is not in the file, an allocation that its contract
  takes or hands over through a pointer or a global (<<blocks-through-memory>>);
* two pointers in a loop's invariant that each own an allocation through a
  parameter's pointee (`+*pp+` and `+*qq+`) verify, but slowly; a loop that calls a
  function borrowing the allocation of `+*pp+` needs `+*pp == keep+` in its invariant;
  and an owner that takes a block in a loop on some iterations only needs an
  invariant that says when (<<owning-locals>>);
* `vlibc_realloc`, `vlibc_aligned_alloc`, `vlibc_free_sized` and
  `vlibc_free_aligned_sized`, which have no contract yet
  (`call_without_contract`), a block of vlibc's allocator named by
  `cerastes::owning` or `cerastes_owns_block` (they name the platform's
  allocator; `cerastes_owns_vlibc_block` is the spelling for vlibc's), and
  `vlibc_malloc`, `vlibc_calloc` and `cerastes_owns_vlibc_block` in pass:[C++]
  (<<vlibc-allocator,vlibc's allocator>>);
* `restrict` except on a C parameter whose contract owns its object;
* `void *` other than an allocation's result converted at once to `T *` and
  the argument of `free` (<<heap>>), and pointers to unions, to functions and to
  structures that are not supported;
* `restrict` beside a parameter or global that can hold a pointer of the same
  type (a pointer to a pointer, a structure with a pointer member, a pointer
  global), and on a pointer to a structure;
* conversions between pointer types other than adding `const` to the object
  pointed to, comparisons of order and arithmetic on pointers.

In C, the compiler's warnings about pointers of incompatible types
(`long *q = &i;` for an `int i`) are errors under `cerastes verify`.
