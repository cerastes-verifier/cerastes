= Integer semantics

This page says what cerastes proves about integer arithmetic. It describes one
meaning for each expression, used for C23 and for pass:[C++]20 alike, so a
`.c` file verifies, or fails, the same way in both modes. Where the two
standards differ, cerastes takes the stricter rule. Each rule below says what
is an error, and every error is reported at the operator with the category
named in xref:error-messages.adoc[Error messages].

In short:

* arithmetic that does not fit its type is an error, signed or unsigned:
  nothing wraps;
* a conversion that does not fit its target type is an error, with or without
  a cast;
* division by zero, and a shift whose count or result is out of range, are
  errors;
* operands narrower than `int` are promoted, as in C and pass:[C++], and that
  has consequences you can prove or trip over;
* a value of an enumeration is always one of its values, and a conversion into
  an enumeration that may not give one is an error.

== Types and ranges

The integer types are `bool`, `char`, `signed char`, `unsigned char`, `short`,
`int`, `long`, `long long` and their unsigned forms, `wchar_t`, `char8_t`,
`char16_t`, `char32_t`, and `+__int128+` with `+unsigned __int128+`. Their sizes
and whether plain `char` is signed come from the compiler's description of the
target (on macOS for Apple silicon and on x86-64 Linux `int` is 32 bits, `long`
is 64 and plain `char` is signed), never from constants inside cerastes.

A value of a type is always inside its range. A parameter is assumed to be in
the range of its type when the function starts, and cerastes proves that every
result, and every value an operation produces, is in range too.

Enumerations have their own range, described in <<enumerations>>.
`_BitInt`, floating point and vector types are rejected in this version
(xref:verifying.adoc#not-supported[the list of constructs not yet supported]).

A character literal with more than one character (`'ab'`) is rejected: its value
is up to the compiler, and a longer one (`'abcde'`) or a wide one (`L'ab'`) loses
characters. So is a `u'...'` literal whose character does not fit in 16 bits, and
an escape too large for its type (`'\x100'`, `'\400'`).

A character literal is the code it names, converted to its character type: `'a'`
is 97 and `'\x7f'` is 127. A code that does not fit is a `conversion` error at
the literal, on the paths that reach it: plain `char` is signed here, so
`'\xff'` would be the `char` -1 (an `int` -1 in C), and `L'\xffffffff'` the
`wchar_t` -1. Write the number instead (`255`, `(unsigned char)0xff`), or, in
C23, `u8'\xff'`, which is the `unsigned char` 255. `(unsigned char)'\xff'` is
reported too: the literal is converted to `char` before the cast.

== Unsigned arithmetic is checked too

C and pass:[C++] define unsigned arithmetic modulo 2^N^, but cerastes does
not wrap: an integer always means the mathematical value of the expression
that computed it. So `+`, `-`, `*`, `pass:[++]`, `--` and the compound
assignments on an unsigned type must produce a value that fits the type, or
cerastes reports `overflow` at the operator, exactly as for a signed type.

[#conversions]
== Conversions

[cols="2,5"]
|===
| Conversion to | Rule

| an integer type, signed or unsigned
| the value must fit, otherwise `conversion`; this holds for an implicit
  conversion and for a cast written by you (`(short)x`, `static_cast<short>(x)`,
  `(unsigned)x`), and for an initialization, an assignment, a compound
  assignment, an argument and a return value

| an enumeration
| the value must be one of the values of the enumeration, otherwise
  `conversion`; this holds for a cast, for C's implicit conversions, and for an
  enumeration whose underlying type is unsigned (<<enumerations>>)

| `bool`
| `v != 0`
|===

Both standards define the conversion of an out-of-range value to an unsigned
type as modular, pass:[C++]20 does the same for a signed type, and C23 leaves
that to the implementation. cerastes makes every one of them an error, in both
modes, which is also what VeriFast does by default. A conversion that cannot
lose anything (the source range lies within the target's, or the value is a
constant that fits) needs no check.

== Promotions and the usual arithmetic conversions

C and pass:[C++] compute with operands of rank lower than `int` in `int`.
cerastes follows them exactly, so these faithful consequences apply:

* the product of two `unsigned short` values is computed in `int`, and can
  overflow it;
* `unsigned char` operands promote to `int`, so the sum of two of them always
  fits, and converting it back to `unsigned char` must fit too: `uc + uc` stored
  into an `unsigned char` is a `conversion` error unless the sum is at most 255;
* when `int` meets `unsigned`, the `int` converts to `unsigned`, and that
  conversion is checked: `-1 < 0u` and `i + 0u` for a negative `i` are
  `conversion` errors.

== Shifts

The count of a shift must be at least 0 and less than the width of the
promoted left operand; otherwise it is `shift`. Left shift of an unsigned value
must give a result that fits, otherwise it is `shift`: no bits are dropped.
Left shift of a signed value must have a non-negative left operand and a
result that fits; pass:[C++]20 would define more, but cerastes uses C23's stricter rule
in both modes. Right shift of a negative value is arithmetic (it rounds toward
negative infinity): defined in pass:[C++]20 and what this target does in C23.

[#bitwise]
== Bitwise operators

`&`, `|`, `^` and `~` have their two's complement meaning on the values of their
operands. `&`, `|` and `^` compute in the type the usual arithmetic conversions
give, and `~` in the promoted type of its operand, as the compilers do. Their
result always fits that type, so they report nothing: `+-8 & 13+` is 8, `+~0+` is
-1, `+~x+` is `+-x - 1+` for a signed `x`, and `+(-1) ^ INT_MAX+` is `INT_MIN`.

The compound assignments `&=`, `|=` and `+^=+` compute the same way and convert
the result back to the type of their left operand, which must fit
(<<conversions,Conversions>>): `+uc = ~uc+` on an `unsigned char` is a
`conversion` error, since `+~uc+` is a negative `int`, and so is `sc |= 0x80`
on a `signed char` that is not negative.

Mind the type of a mask. With an `unsigned u`, `+u & ~7+` is a `conversion`
error: `+~7+` is the `int` -8, and converting it to `unsigned int` does not fit.
Write the mask in the type you mean, `+u & ~7u+`:

Likewise, `+x & -x+` (the lowest set bit) is an `overflow` error for an `unsigned
int` `x` that is not 0, at the unary minus; for a signed `x > 0` it is fine.

A mask by a constant of the form 2^k^ - 1 (`1`, `255`, `0xFFFFFFFF`, `INT_MAX`)
keeps the low k bits of the other operand, and a mask by its complement (`~15`,
`~0xFFu` with an `unsigned int` operand, `INT_MIN`) clears them. The constant is
taken in the type the operation computes in, after the usual arithmetic
conversions: with an `unsigned long long` operand, `~0xFFu` is 0xFFFFFF00, which
is neither form. cerastes reads such a mask as the remainder by 2^k^ (always
between 0 and 2^k^ - 1, for a negative operand too) or the operand minus that
remainder, which is what the bits give, so what it means is decided for every
operand, as long as the mask is written as a constant in the expression (a mask
passed as an argument is not): `+v & 0xFFFFFFFF == v % 4294967296+` for an `unsigned long
long v`, `+x & ~15 == x - x % 16+` for `x >= 0`, and `+x & 255+` for a negative
`x` (it is `x % 256 + 256` when that remainder is not 0, since C's `%` keeps the
sign of `x`):

[source,c]
----
include::example$integer-semantics/mask_remainder.c[tag=source]
----

`|` and `+^+` with the same constants are decided the same way, on either side and in
`|=` and `+^=+`. A mask of the form 2^k^ - 1 sets (`|`) or flips (`+^+`) the low k bits:
`+x | 255+` is the operand with its remainder by 256 replaced by 255, and `+x ^ 255+`
replaces that remainder r by 255 - r. A mask by the complement keeps the low k
bits and sets or flips every higher one (`+x | ~15+`, `+u ^ ~0xFFu+` in the type of
`u`). So `+(x ^ 255) ^ 255 == x+` is proved for every `x`, and so are these:

[source,c]
----
include::example$integer-semantics/mask_or_xor.c[tag=source]
----

Through a chain of such masks, a bound on the result is decided at any depth, and so is an identity whose masks cancel
in adjacent pairs (`+(((x ^ 255) ^ 255) ^ 15) ^ 15 == x+`, to six masks for a signed type, at every depth measured for
an unsigned one). An identity through a signed chain whose masks alternate
(`+(((x ^ 255) ^ 15) ^ 255) ^ 15 == x+`), or a longer one, may run to the time limit, like the undecided shapes below.

What the prover decides about other bitwise results is limited in this version.
It decides every expression of constants, the range of a result, a result named in
a contract (`r == (a & b)`), and a bound by a constant mask (`+u & 255+` is at
most 255). It does not decide other relations between a bitwise result and
arithmetic on the same variable, or identities that need the bits of a variable in
general: `+(u | 4) & 4 == 4+` (4 is not a mask), `+x & x == x+`,
`+(a ^ b) ^ b == a+` for two variables (the swap by XOR), `+u & m <= m+` for a variable mask `m`,
or the bounds of `+x & -x+`; nor, for `+__int128+`, a constant operand written as a
shift of a constant other than 1 (`+(__int128)2 << 100+`; write `+(__int128)1 << 101+`).
A claim that needs one of them is not proved or
refuted: verification runs until its time limit (`--timeout`, 300 seconds by
default) and ends with exit status 3, "not checked", never with a verdict
(xref:verifying.adoc[Verifying a program]). For such a claim, a caller with
constant arguments is decided.

The shapes the compilers warn about with `-Wall` are rejected, in both modes and
also in annotations (as for xref:verifying.adoc#side-effects[side effects]):

* a comparison, a `{plus}` or `-`, or another bitwise operator as an operand of `&`,
  `|` or `+^+` without parentheses (`+a & b == c+`, `+a | b & c+`);
* `!x` as the left operand of `&` or `|` (`+!x & y+`), unless the right operand
  is a truth value too;
* `+~+` of a truth value (`+~(x > 0)+`, or a `bool`);
* a `?:` whose condition is `&` or `|` with a truth value on its right
  (`+a & b > 0 ? c : d+`);
* `&` or `|` of two truth values that both have a side effect
  (`+f() & g()+` for `bool` results);
* a comparison of a masked value with a constant it can never equal
  (`+(x & 2) == 1+`), and `+x | 4+` used as a condition;
* `+2 ^ 32+` and `+10 ^ 3+`, which are not powers, however the constants are written;
* `&`, `|` or `+^+` of two truth values compared with a constant other than 0
  and 1 (`+(p ^ q) == 2+`), like any truth value
  (xref:verifying.adoc#warning-shapes[Shapes the compilers warn about]).

== Annotations mean their C value

An annotation is an expression of the program's language, and it means what
that expression computes. Overflow, signed or unsigned, a division by zero, a
bad shift or a conversion that does not fit in a contract is an error at the
annotation's line, with the same category as in
code. Each clause is checked under the clauses before it, so a `requires` may
rely on an earlier `requires`, and an `ensures` on every `requires` and the
earlier `ensures`.

The compiler's own warnings for these (overflow in a constant, a bad shift
count, a division by zero, a sign change, a truncation, a missing `return`) are
not shown by `cerastes verify`: the verifier reports each problem itself, once,
with its category. A `#pragma` that changes a warning cannot hide a problem
from it: the front end's diagnostic pragmas are refused in the files it
verifies.

A named constant, a `const` global, is checked the same way: its initializer as
you wrote it, whether or not anything uses it, so `const short limit = 70000;`
is a `conversion` error at its line
(xref:verifying.adoc#constants[Named constants]). So is the condition of a static
assertion, which the compiler has accepted in its own arithmetic:
`static_assert(65536u * 65536u == 0u)` is an `overflow` error
(xref:verifying.adoc#static-assertions[Static assertions]).

[#enumerations]
== Enumerations

An enumeration and its enumerators are verified in both modes. Each
enumeration has a range of values:

* an enumeration whose underlying type is fixed (`enum small : unsigned char`,
  and every pass:[C++] `enum class`, whose underlying type is `int` unless you
  write another) has the values of that type;
* any other enumeration has the values of the smallest bit-field that holds
  all its enumerators, as in pass:[C++]: `enum color { RED, GREEN, BLUE }` has
  the values 0 to 3, `enum sign { NEG = -1, ZERO, POS }` the values -2 to 1.

A value of an enumeration is always in that range. A parameter is assumed to
be in it, a result must be in it, and every conversion into an enumeration
must give a value in it, or it is a `conversion` error: a cast you write, and
in C an integer stored into an enumeration without a cast. A value in the
range need not be an enumerator: `(enum color)3` is fine. C itself lets an
enumeration hold any value of an integer type the compiler picks for it, so
this rule is stricter than C, and it is the same in both modes.

An enumerator is its value. In C an enumerator is an `int` and in pass:[C++]
it has the enumeration's type, but because every value of an enumeration lies
in the range of `int`, comparing with `==` and `!=`, a `switch`, and storing an
enumeration value into an integer variable, argument or result mean the same in
both languages, and so does arithmetic on enumerators (`GREEN + 1`). An
enumerator's initializer is checked as you wrote it, like a named constant's:
`enum { S = (signed char)300 };` is a `conversion` error at its line.

Arithmetic on an enumeration value is where the two languages part: C
computes `c - 1` in `unsigned int` for `enum color` (so 0 - 1 is the largest
`unsigned int`), pass:[C++] in `int` (so it is -1). cerastes therefore rejects
an enumeration value that the compiler converts to an integer for arithmetic,
for a unary operator, for a shift or for an arm of `?:`. Write the conversion
yourself (`(int)c - 1`) to say which you mean. Compound assignment, `pass:[++]`
and `--` on an enumeration are rejected too. Arithmetic on enumerators of two
different enumerations (`pass:[RED + NA]`) and a `?:` whose arms are
(`x ? RED : NA`) are rejected in both modes, as pass:[C++]20 deprecates them
(xref:verifying.adoc#warning-shapes[Shapes the compilers warn about]); convert
one side (`pass:[(int)RED + NA]`).

An `==` or `!=` between an enumeration value and a signed integer that may be
negative is rejected, in both modes. In C an enumeration without negative
values is compared as `unsigned int`, so `c == x` converts `x` to `unsigned
int`, and both clang and GCC warn about it (`-Wsign-compare`). Write the
conversion you mean, for example `(int)c == x`. A constant that is not negative
(`c == 1`), an enumerator of an enumeration without a fixed unsigned type
(`GREEN == x`), a comparison or other truth value
(`c == (x > 0)`, also a `?:` whose arms are truth values, `c == (x ? true :
false)`, or a comma whose last operand is one), and a `bool`, `unsigned char` or
`long` operand are fine.
Comparing values of two different enumerations with `==` or `!=` is rejected
as well, as every compiler warns about it; convert both sides (`(int)c ==
(int)n`). A `?:` whose arms are enumerators (`x ? RED : GREEN`) has the
enumeration's type in pass:[C++], and a `?:` whose result is an enumeration is
rejected there; C gives it the same verdict in `==` and `!=`, so
`c == (x ? RED : GREEN)` is rejected in both modes:

include::example$integer-semantics/enum_compare_signed.c[tag=source]

The order of two values of the same enumeration can be compared (`<`, `<=`,
`>`, `>=`), and so can a value and one of its enumerators: both languages
compare the same two integers. Comparing the order of an enumeration value with
any other integer is rejected, even with a constant: C compares `c < -1` in
`unsigned int` for `enum color`, where it is true, and pass:[C++] in `int`,
where it is false. Write the conversion (`(int)c < 2`). A pass:[C++] `enum
class` has no implicit conversions; its values can be compared with each other,
