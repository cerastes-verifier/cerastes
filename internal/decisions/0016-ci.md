# 0016 — Continuous integration: the full `check.sh` on GitHub's `xcode-27` runner (S2)

- **Status:** accepted for S2. Owner decisions (2026-10-21): GitHub's standard `xcode-27` runner; the full
  `scripts/check.sh` on pull requests, pushes to `main` and `workflow_dispatch`; the owner pushes, the session
  watches the runs read-only; drift on the runner stops the work and goes to the owner. In the S2 planning round:
  the runner's **Command Line Tools**, not Xcode 27.0 (item 2); the first runs come from a draft pull request the
  owner opens (item 4); `check.sh`'s VIR line loses its hard-coded `-j 8` (item 8); the owner reinstalled Homebrew
  `gcc` so that the Mac and the runner use the same GCC bottle (item 3).
- **Milestone:** S2 (2026-10-21), between M4.2a and M4.2b.

## Context

Until S2 only the docs had CI (0004 item 4): `check.sh`, the build, the lints, the harness self-tests, every
verifier test and the walker oracle ran on the owner's Mac only. M4.1, M4.2a and the box sessions showed how much
depends on the exact toolchain (the SDK headers EDG parses, `assert`'s macOS expansion, the clang version EDG
emulates, GCC for the native-ok runs), so CI must run on the same toolchain or say exactly where it differs.
GitHub's macOS arm64 images are the only hosted runners that can run `scripts/bootstrap.sh` (Darwin on arm64,
Homebrew, the Command Line Tools). Facts checked while planning (runner-images readme, image `20261012.0260.1`;
GitHub's runner reference):
- `xcode-27`: macOS 27.0.1, 3 M1 cores, 7 GB RAM, 14 GB SSD; Xcode 27.0 (`27A266a`, the default), 27.1 RC and 27.2
  beta; SDKs 27.0 and 27.2; **Command Line Tools 27.0.0.0.1788430756**, the owner's exact package; Homebrew GCC 13,
  14 and 15 (no 16); JDKs 11, 17, 21, 25 (none from Homebrew); no sbt, no shellcheck; Node 24; Python 3.15.0.
- The label is a **public preview**, not generally available (the S2 handoff said GA): GitHub serves preview images
  as-is, without its service-level terms. It is still the only image with the 27.0 tools.
- No expectation in `tests/` or `doc/` (expect lines, the 134 goldens) embeds machine data: no absolute paths, SDK
  or clang versions. The emitted `.vpr` files and their maps contain no absolute paths. Xcode's SDK 27.0 and the
  Command Line Tools' SDK 27.0 have byte-identical `usr/include` on the owner's Mac.

## Decision

1. **Runner and workflow.** `.github/workflows/ci.yml`, one job on `runs-on: xcode-27`. Triggers: `pull_request`
   (no path filters: every change can affect a verdict), `push` to `main`, `workflow_dispatch`. Permissions:
   `contents: read` only, and checkout keeps no credentials. Actions are pinned to full commit SHAs with the
   release in a comment (0001, "GitHub Actions"; Dependabot proposes updates). The job log records the image
   version (`ImageVersion`); a preview image that GitHub rebuilds is noticed through the assertions of item 2, not
   trusted.
2. **Toolchain: the runner's Command Line Tools** (owner). The job sets
   `DEVELOPER_DIR=/Library/Developer/CommandLineTools`, the toolchain the owner builds and tests with, so the
   compiler, the SDK and every path `bootstrap.sh` scrapes are the owner's. `scripts/ci.sh` asserts, and fails the
   job otherwise:
   - the `com.apple.pkg.CLTools_Executables` package version `27.0.0.0.1788430756`;
   - `clang` on `PATH` is `/usr/bin/clang` (EDG's preset builds with `CC=clang`, and bootstrap's include and version
     scrape runs `clang`), and `xcrun -f clang` is the Command Line Tools' clang;
   - the banner `Apple clang version 21.0.0 (clang-2100.3.34.2)`;
   - SDK version 27.0, whose real path is `…/CommandLineTools/SDKs/MacOSX27.0.sdk`;
   - after bootstrap, `build/env.sh` names the Command Line Tools' `clang++` and `EDG_CLANG_VER_SCRAPE` is 210000.
   The Xcode apps on the image are not used. A failing assertion is never loosened to fit the runner: when the image
   changes its tools, the owner decides, and the assertion and 0001 change together. Rejected: Xcode 27.0, whose
   clang build number is not the owner's and whose paths cannot be rehearsed on the owner's Mac.
3. **GCC** (the native-ok runs, 0008). The image has no GCC 16, so `ci.sh` installs Homebrew `gcc` when `g++-16` is
   missing, and asserts major version 16 and that `gcc-16 -print-sysroot` exists. The owner's GCC was a macOS 26
   bottle whose sysroot was the SDK 26.5; Homebrew now serves only the macOS 27 bottle, whose sysroot is
   `CommandLineTools/SDKs/MacOSX27.sdk` (SDK 27.0), and the owner reinstalled it (2026-10-21), so both machines
   compile the native-ok runs with the same GCC against the same SDK. When Homebrew's `gcc` moves to 17, CI moves
   deliberately to `gcc@16` (or the owner moves both machines), recorded here and in 0001.
4. **The first runs** (owner). `workflow_dispatch` runs only workflows that exist on the default branch, and the
   push trigger is `main` only, so before `ci.yml` reaches `main` it runs on a draft pull request the owner opens
   from the session branch. A pull request's runs use the workflow file of its merge commit.
5. **Concurrency.** Pull requests cancel their superseded runs; runs on `main` never cancel and each gets its own
   group (`ci-main-<run_id>`), because a shared group, even without `cancel-in-progress`, keeps only one pending
   run and drops the older one.
6. **Checkout: full history, submodules included** (`fetch-depth: 0`, `submodules: recursive`). `check.sh`'s first
   step, `edg_tree.py check`, requires `refs/remotes/origin/cerastes` in `third_party/edg` and the pin to be its
   ancestor (0009); a depth-1 submodule clone is single-branch and has neither. EDG's full history is about 0.3 GB,
   no more than one checkout of its 3.7 GB tree, and leaves no shallow or partial-clone state for `edg_tree`'s
   status and diff calls. `ci.sh` asserts that the submodule is not shallow and that the ref exists. An unpushed
   fork therefore fails the job in its first minutes, which is the point: CI checks what a fresh clone gets.
7. **Steps and caches.** `scripts/ci.sh` sets the runner up (the assertions above, the GCC install, the full
   `scripts/bootstrap.sh`); `scripts/check.sh` runs unchanged as its own step afterwards, so a failing test run still
   saves the cache. Caches hold inputs, never cerastes or EDG build outputs:
   - npm, through `actions/setup-node`;
   - Silicon's jar and `build/silicon.stamp`, keyed on the silicon and silver gitlinks and on
     `scripts/bootstrap.sh` (which names the JDK formula the stamp records), restored before `ci.sh` and saved after
     it; bootstrap rebuilds when the restored stamp does not match. Silicon's and silver's `target/` are ignored by
     their own `.gitignore`, so the stamp's dirty count stays 0.
   - Not cached: Z3 (a few seconds to download, and its SHA-256 is checked on every run), sbt's and Coursier's
     caches (only used when the jar cache misses), and every EDG and cerastes build directory (always built from
     scratch, which is what a fresh clone does).
   Python is 3.14 through `actions/setup-python` (the owner's 3.14.7; the image's default is 3.15) and Node the major
   in `doc/.node-version` through `setup-node`. JDK 17, sbt and shellcheck come from Homebrew through bootstrap, as on
   the owner's Mac. CMake, Ninja and bash are the image's, recorded in the job log, not pinned (as in 0001).
   `ci.sh` sets `HOMEBREW_NO_AUTO_UPDATE`, `HOMEBREW_NO_INSTALL_UPGRADE` and `HOMEBREW_NO_INSTALL_CLEANUP`, so a
   rehearsal on the owner's Mac installs nothing that is already there. It fails when `JAVA_TOOL_OPTIONS`,
   `_JAVA_OPTIONS`, `JDK_JAVA_OPTIONS`, `SDKROOT`, `CC`, `CXX`, `CPATH`, `LIBRARY_PATH` or `CERASTES_EDG_SRC` is set
   (each would change what the harness or the compilers do).
8. **Job count and memory.** `run_tests.py` and `mutate.py` take their default `-j` from `CERASTES_JOBS` when it is
   set (a positive integer; anything else is a usage error), else half the cores as before; the job sets 3.
   `check.sh`'s VIR line no longer hard-codes `-j 8` (owner): it uses the same default, still 8 on the owner's
   16-core Mac and 3 on the runner, where eight Silicon JVMs (default heap up to a quarter of 7 GB each) would
   overcommit memory. `check.sh`'s own lines are otherwise unchanged and still pinned by the harness self-test.
9. **Time.** `timeout-minutes: 240` while CI is brought up: the estimate on 3 cores is 85–140 min (two cold EDG
   builds, Silicon, the tests at `-j 3`). After two green runs it is tightened to the larger of 150 and 1.5 times
   the measured time. The driver's 300 s Silicon limit and the harness's 600 s limits are unchanged: a test that hits
   one on the runner is drift (item 10).
10. **Drift policy.** Any result on the runner that differs from the local one (a test, a count, a golden, a
    diagnostic, a timeout) stops the work and goes to the owner. CI never edits an expectation, never reruns a job to
    get it green (a flaky result is drift too), and never runs `--update-golden` or `CERASTES_EDG_SRC`. The
    harness self-test guards both workflow files and `ci.sh` the way it guards `check.sh` and `docs.yml`: the steps
    run as active, unconditional lines with no `|| true`, `set +e`, `continue-on-error` or job-level `if:`, every
    action is pinned to a SHA, and the toolchain assertions cannot be dropped or weakened.
11. **Expected differences.** A fresh clone's harness self-test reports one more skip than the development tree
    (`test_the_real_site_has_no_chrome_pre_or_backticks` needs `build/doc`, which `check.sh` builds after the
    self-test; the same check then runs on the real site in `check.sh`'s docs step). CI's counts are therefore
    compared with a local rehearsal in a fresh clone, not with the development tree. Every test's emitted Viper is
    compared byte for byte: the job uploads `build/vpr`.
12. **Docs.** `docs.yml` keeps building and deploying the site (0004); `ci.yml` builds the docs again inside
    `check.sh` and runs every doc example as a test. Nothing user-visible changes, so `doc/` gets no page
    (invariant 8); `tests/README.md` describes CI and `CERASTES_JOBS`.
13. **Fallback: x64 Linux in Docker** (recorded, not built). It needs: the encoder to recognise glibc's `assert`
    expansion (`__assert_fail`, 0015 item 6 accepts only the macOS shape); `src/driver/silicon.cpp` without the
    clang-only `__builtin_available` and the macOS `posix_spawn_file_actions_addchdir`; a Linux `bootstrap.sh`; the
    Linux `GNU_VECTOR_TYPES_ALLOWED` value in `check_edg_config.sh`; and every SDK-dependent expectation (67 tests
    include system headers) re-established against glibc and libstdc++ or libc++. Use it only if the macOS images
    stop matching the owner's toolchain.

## Consequences

- Every pull request and every push to `main` runs the whole of `check.sh` on a clean machine with the owner's
  toolchain, so "green on the owner's Mac" is no longer the only evidence.
- A pin that is not pushed (`NOT YET PUSHED`) fails CI by design.
- Dependabot's weekly action and npm updates now run the full check.
- Amends 0004 item 4 ("CI runs only the docs") and 0001 (the runner, the host toolchain, GCC, Python, the new
  actions).
